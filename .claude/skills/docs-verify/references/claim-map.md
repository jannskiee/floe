# Claim map

Keyed by the symbol that is the truth. For each sentence you touched, open the symbol and diff the sentence against it. No values are written here on purpose: a value in this file would go stale the day the code changes, and the point is to read the code. "Script" means docs-check.mjs already compares it; everything else is read by hand.

The map names where a value is stated; grep the old literal repo-wide before finishing, the map is not exhaustive.

## Relay cap

- `RelaySizeLimit` (cli/engine/transfer/relay.go) and `RELAY_SIZE_LIMIT` (client/lib/relay.ts); the comparison is strictly greater-than. The sender gates every transfer (`checkRelayGate`, `evaluateRelayGate`). A Go receiver also gates a request-link drop when `ReceiveLimits.HostRelayCheck` is set (the field is in cli/engine/transfer/limits.go; receiver.go probes once at accept through `hostRelayVerdict`, then holds every file and frame to `checkRelayGate` and `relayFrameCheck`, all three in relay.go); only `requestLimits` in desktop/transfer.go sets it.
- `RELAY_CAP` (client/lib/howItWorksStrings.ts) is `formatBytes(RELAY_SIZE_LIMIT)` and is what /how-it-works prints; its test pins it to "2 GB", so a change to client/lib/relay.ts fails the client suite. The Go constant is not read by the client, so only this map couples the two.

## Integrity hash

- `validSHA256Hex` and `parseEnd` (cli/engine/transfer/control.go) define the wire digest (64 lowercase hex) and the rule that a present but unreadable digest refuses the file; `normalizeSha256` and `verifiedCountOf` (client/lib/transfer/protocol.ts) are the browser twins, and `endMessage` emits the key only for a valid digest.
- The `Verified` row, "SHA-256 matched", comes from the summary in `ReceiveFilesWithOptions` (receiver.go: `verifiedCount == filesReceived && filesReceived > 0`) and `SendFilesWithOptions` (sender.go: `hasVerified && verified == len(files)`). The digest is taken while writing, never re-read from disk, and on the sender the row is the receiver's report rather than a proof. A mismatched or unreadable digest deletes the .part before the rename and refuses with `CodeHashMismatch`.
- `FileDone` and `OnFileDone` (receiver.go) are what a GUI learns per committed file.
- Whether a sender hashes is decided by `sendFileHashes` (cli/engine/transfer/sender.go, P0-22) and `SEND_FILE_HASHES` (client/lib/transfer/protocol.ts, P0-21b), so docs say "when the sender provides one"; both receivers report `verified` on their `received` frame (the browser through `receivedMessage` in `confirmBatch`, client/lib/transfer/receiver.ts, since SG-01), always present and 0 when no file matched.
- The browser's two hash waits (client/lib/transfer/protocol.ts): `hashBoundMs` (size at 10 MB/s plus 30 s), `END_DIGEST_WAIT_MS` (a sender sends `end` without `sha256` once it has waited this long after the last chunk, under a Go receiver's `receiveStallTimeout`) and `POST_END_HASH_WAIT_MS` (a receiver with more files to come keeps a file unverified past it, under the senders' 120 s ack wait; the last file keeps `hashBoundMs`). `TestBrowserHashWaitsFitGoClocks` (cli/engine/transfer/deadlines_test.go) pins the Go side of both. Docs: docs/how-it-works/file-checks.mdx "When a browser runs out of time" (the reader-facing home of both waits), docs/reference/transfer-protocol.mdx (the `end` section and the paragraph under "Timeouts"), docs/reference/limits.mdx "Timeouts" (the SHA-256 row), docs/changelog.mdx (the Web app SHA-256 bullet). The pages that used to repeat the waits (docs/how-it-works/known-limitations.mdx, docs/web-app/receiving.mdx, docs/cli/receive.mdx, docs/desktop/request-links.mdx) now give a clause and link to file-checks; keep them that way.
- Tests: the `endSha256` and `receivedVerified` rows of the parity table (cli/engine/transfer/parity_test.go and client/lib/transfer/parity.test.ts), cli/engine/transfer/hash_test.go.
- Docs: docs/how-it-works/file-checks.mdx (the whole page: who hashes and when, what a mismatch does, "What you see in each app", "When there is no mark", and what the checks do not prove), docs/reference/transfer-protocol.mdx "Integrity" and the `end` and `received` field tables, docs/how-it-works/known-limitations.mdx, docs/how-it-works/encryption.mdx, docs/cli/receive.mdx (the summary example, the `Verified` row paragraph under "Output", and "Files are written as `.part` first"), docs/cli/send.mdx (the Verified row paragraph under the Sent box), docs/desktop/request-links.mdx "The check mark", docs/web-app/request-links.mdx "When the files arrive", docs/web-app/sending.mdx "When it finishes", docs/web-app/receiving.mdx, docs/desktop/sending.mdx, docs/desktop/receiving.mdx, docs/quickstart.mdx (each shows the mark or the row and links to file-checks), CLAUDE.md "Transfer Protocol Versioning", the Store What's new draft.

## Delivery confirmation (the ack's confirms)

- The ack map in `ReceiveFilesWithOptions` (cli/engine/transfer/receiver.go) sets `confirms: true` on every Go receiver's ack; `parseAckConfirms` (sender.go) reads it from the first file's ack, by its exact key and as the literal `true` only, and `SendFilesWithOptions` then runs the delivery wait as `SendOptions.RequireReceived` does: success only on `received`, a refusal returns its `*PeerStoppedError`, and a close returns `ErrClosedBeforeReceived`. Without the field (browser receivers of web app 1.11.1 or earlier, Go receivers before FT-GO-CONFIRMS step 2) the wait still ends in success at a drained buffer. Additive and optional: `ProtocolVersion` stays.
- `ackConfirmsOf` and `Ack.confirms` (client/lib/transfer/protocol.ts) are the browser twin; the browser sender does not act on it. The browser receiver sets it on every ack through `ackMessage`'s explicit `confirms` parameter while `RECEIVER_CONFIRMS` (protocol.ts, the rollback lever beside `SEND_FILE_HASHES`) is on, and keeps the promise in `confirmBatch` (client/lib/transfer/receiver.ts): `received` with this batch's matched count once its own count of handed-over files reaches `total` and every part has read back, as the last step of `complete()`, in its own try (SG-01). It changed every released Go sender's ending against floe.one on deploy, not on a tag.
- The wait has no deadline of its own. Its bound is `peer.Connection.Failed` (cli/engine/peer/connection.go: closed once on the failed state, about 30 s after the last packet, never on disconnected), watched by `closeOnFailed` (cli/cmd/floe/connfailed.go) in floe send's `runSend` and by `watchConnFailed` (desktop/requestconn.go) in the desktop's `runSend`. A receiver that keeps its connection alive and never answers holds a send until the person cancels.
- What a person sees: floe send prints the error's own text (`ErrClosedBeforeReceived`, "the connection closed before the receiver confirmed delivery", or the refusal's `PeerStoppedError` sentence); the desktop maps the close through errors.ts's `connection closed` rule to its lost-connection line.
- Floe Desktop's send endings after desktop-v0.3.0: `sendEnd` (desktop/transfer.go) hands a `*transfer.PeerStoppedError` over without the `transfer failed: ` wrapper and keeps the relay-cap handling, and desktop/frontend/src/errors.ts maps "They stopped this drop" and "The drop stopped on their computer" to "They stopped the transfer" (A8b-B3), and `ErrNoFiles` ("no files to send", from `Summarize` at the click) to "The folders you chose have no files to send" (A3-B4); "no files selected" keeps its own words. Docs: docs/troubleshooting.mdx "They stopped the transfer" (the Floe Desktop heading) and `no files to send`.
- Tests: the `ackConfirms` rows of the parity table (cli/engine/transfer/parity_test.go and client/lib/transfer/parity.test.ts), `FuzzParseAckConfirms`, the confirms tests and `TestPlainSendWithoutConfirmsEndsAtDrain` in cli/engine/transfer/requirereceived_test.go, the ackConfirmsOf and receivedMessage blocks of client/lib/transfer/protocol.test.ts, client/lib/transfer/receiverConfirms.test.ts, and the CLI-sender exit and `Verified` assertions of client/e2e/cli-interop.spec.ts (Direction 1) and client/e2e/back-compat.spec.ts (released CLI to HEAD browser).
- Docs: docs/reference/transfer-protocol.mdx ("The end of a batch depends on what the receiver promised." bullet and "How a send ends", the `ack` example and fields, the `received` section), docs/how-it-works/file-checks.mdx "Delivery confirmation" and "When there is no mark", docs/cli/send.mdx (the Verified paragraph, "When a send ends", the two delivery rows of the messages table), docs/cli/flags.mdx "What success means for a send", docs/web-app/sending.mdx "When it finishes", docs/troubleshooting.mdx "the connection closed before the receiver confirmed delivery" (the `ErrClosedBeforeReceived` text as its heading) and `connection closed mid-transfer`, docs/self-hosting/operations.mdx "What an older web app shows" (the File checks row), the FAQ answer in client/components/layout/FAQSection.tsx, CLAUDE.md "Transfer Protocol Versioning".

## Receiver limits

What Floe Desktop and `floe receive` let a sender's file description ask of the disk, checked before anything is written. A browser receiver has no disk path and applies only the message cap and the display cap.

- cli/engine/transfer/control.go: `controlMsgMax` (the one message a file's name, its folder path and the rest of its description have to fit in; `CONTROL_MSG_MAX` in client/lib/transfer/protocol.ts is its twin, and the sentence a receiving browser shows past it is typed twice in client/lib/transfer/receiver.ts) and `maxAnnouncedSize` with `byteCount` (the largest size a sender can announce; `metadataProblem` is the browser twin).

## Room seal

- server/server.js: the seal check in `handleJoinRoom` (after the leave-first block: refuse when the room's `roomMeta` record holds two keys and not the joiner's), the key added in `handleSignal` once a signal passes the room and target checks (the create branch starts the set empty and a join never adds to it, so only a peer that has routed a signal counts), and `roomMeta.delete` in `destroyRoom` (the seal lasts exactly as long as the room). The key is `rateKey(ip)` (server/ratekey.js), the same key every per-IP limiter counts under, carried by `createSocketIOPeer` and `createWSPeer`; peers sharing one key are never sealed out, on purpose.
- server/server.js `sealDigest`: `roomMeta` stores an HMAC-SHA256 of each key under `SEAL_SECRET` (random per process, memory only), never the key itself, because a room can outlive the retention the privacy page promises for an IP address. Storing the raw `rateKey`, or an unkeyed hash of it, makes both privacy sentences below untrue.
- Docs: docs/how-it-works/signaling.mdx "A room holds exactly two people" (the freed-seat paragraphs), docs/reference/architecture.mdx (both `room-full` rows and the "A room also seals" paragraph), docs/web-app/sending.mdx "One link, one recipient at a time", docs/desktop/sending.mdx (the one-receiver paragraph), docs/troubleshooting.mdx "A device that changed networks is refused", docs/web-app/receiving.mdx (the changed-network sentence under "The sender has to stay connected"). ## floe version

- `versionCmd` (cli/cmd/floe/update.go) prints its lines in order: the version line from `version`, the docs line (one of the docs URLs the script's `links` check reads) and the hint, only when `selfupdate.CheckAvailable` returns a tag. The hint's wording is fixed and never consults `PMPath`; after `floe` 1.11.0 it names both ways ("run `floe update`, or your package manager's upgrade command"), and `shownVersion` prints every release without its leading v (the tag itself is what `runUpdate` compares and fetches). `errDevBuild`: on a dev build `floe update` is an error (exit 1). Package-manager detection: `selfupdate.DetectPM` (the words, `caskroom` included) and `pmFor`, which also judges the file the command links to (an Intel Mac's `/usr/local/bin/floe` points into `/usr/local/Caskroom`).
- `CheckAvailable` (cli/internal/selfupdate/version.go): `versionCmd` is its only caller, so no other command checks on its own (`runUpdate` calls `LatestVersion` directly, when asked); its local-build and `FLOE_NO_UPDATE_CHECK` returns come before `fromCache`; `cacheTTL` and `apiURL` (cli/internal/selfupdate/selfupdate.go) are the cache lifetime and the address the docs print; `cacheFilePath` is the file under `os.UserConfigDir()`, whose per-system folders the docs list; and the `time.After` in its `select` is the longest it waits for GitHub. A failed request is never cached.
- Why the two lines differ by a leading `v`: `-X main.version={{ .Version }}` in .goreleaser.yml stamps the version without it, while the hint prints the `tag_name` that `LatestVersion` got from GitHub.
- What a Windows `floe update` leaves: `windowsInstall` (cli/internal/selfupdate/install.go) moves the running executable to `updateBackupPath` (`floe.exe.floe-update-old`, a name only floe makes) and clears that name and the `floe.exe.bak` earlier versions used before it renames; `RemoveUpdateBackup`, which `main` (cli/cmd/floe/main.go) calls at every start, removes `updateBackupPath` alone, never a `.bak` (A4-B17, CLI-03). Docs: docs/cli/update.mdx "Script and manual installs".
- `rootCmd.Version` and `SetVersionTemplate` (cli/cmd/floe/main.go) are `--version` and `-v`: cobra prints the one line and runs no command, so there is no docs line, no hint and no request.
- Docs: docs/cli/version.mdx (the whole page: "Output", "The update check", "Alternatives"), docs/cli/installation.mdx "Verify the install", docs/cli/update.mdx "The update hint", docs/cli/flags.mdx (the `--version` row), docs/security-privacy.mdx "On the command line" (the cache file).

## How often a transfer is direct (measured, not decided by code)

- No code decides this claim. It is a measurement: the Umami event `transfer-received` (sent by a browser receiver when every file has arrived, client/components/P2PTransfer.tsx) carries the route as its `connection` property. Read on 2026-10-14 over the last 90 days: of 92 receives with a known route, 60 were direct (65%) and 32 relayed. Test receives cannot be told from real ones, and the transfer audit forces the relay in some of its cells, so the real direct share is higher by an unknown amount. Events from before about 2026-09-04 carry `unknown`: the page did not yet know the route when it sent them. CLI and desktop receivers send no event, so nothing is measured for them.
- What that supports: "most transfers are direct" and "usually". What it does not support: "almost always", or any number. The figure stays out of every page and every site string: the sample is small and it dates.
- Before strengthening the claim, read it again: Umami, website Floe, Events, Properties, event `transfer-received`, property `connection`.
- Docs: docs/how-it-works/direct-connection.mdx (the opening), docs/how-it-works/2gb-limit.mdx (the opening, and "usually connect directly"), docs/faq.mdx, docs/introduction.mdx and docs/glossary.mdx ("direct connection"). The site says it at client/app/how-it-works/page.tsx, client/app/privacy/page.tsx and client/components/RelayFallbackToggle.tsx.
