# Claim map

Keyed by the symbol that is the truth. For each sentence you touched, open the symbol and diff the sentence against it. No values are written here on purpose: a value in this file would go stale the day the code changes, and the point is to read the code. "Script" means docs-check.mjs already compares it; everything else is read by hand.

The map names where a value is stated; grep the old literal repo-wide before finishing, the map is not exhaustive.

## Desktop server probe and the relay guard

- `probeServer`'s three stages and every string in `probeHealth`, `probeAPI` and `describeDialError` (desktop/serverprobe.go). The probe-result table in the docs quotes all of them verbatim and nothing compares them automatically. `probeTimeout` bounds the two HTTP stages only: stage two goes through `signaling.Connect`, which uses `websocket.DefaultDialer` and therefore its own 45-second handshake timeout, so the worst case is not three times `probeTimeout`.
- `ProbeResult.RelayAvailable` and the two pass messages: `Connected` when a relay is offered, and the longer one naming Hide my IP when it is not. `OK` stays true either way, on purpose, so the docs must not describe the relay-less case as a failure.
- `errNoRelay`, `errRelayUnknown` and `requireRelay` (desktop/transfer.go), and `requireRelay` (cli/cmd/floe/main.go) for the CLI's two `--relay-only` wordings. The pair exists because `ice.FetchDetail`'s `degraded` tells "the server said STUN only" apart from "the server was never heard from"; docs that describe only the first are wrong for the second. Both are quoted in docs/troubleshooting.mdx. The desktop pair is anchored in desktop/frontend/src/errors.ts `PASSTHROUGH` by the leading words "Hide my IP needs a relay" (`errNoRelay`) and "relay details for Hide my IP" (`errRelayUnknown`) and asserted whole in errors.test.ts, so rewording either anchor breaks the passthrough silently. - `HasRelay` and `ParseServers` (cli/engine/ice/credentials.go) are the one classifier and the one decoder the probe and both guards share; `HasRelay` delegates to `iceURLClass`, whose cases `TestIceURLClass` pins. `defaults()` has no relay, which is why a non-200 from `/api/turn-credentials` degrades into exactly the case the guards catch.

## Integrity hash

- `validSHA256Hex` and `parseEnd` (cli/engine/transfer/control.go) define the wire digest (64 lowercase hex) and the rule that a present but unreadable digest refuses the file; `normalizeSha256` and `verifiedCountOf` (client/lib/transfer/protocol.ts) are the browser twins, and `endMessage` emits the key only for a valid digest.
- The `Verified` row, "SHA-256 matched", comes from the summary in `ReceiveFilesWithOptions` (receiver.go: `verifiedCount == filesReceived && filesReceived > 0`) and `SendFilesWithOptions` (sender.go: `hasVerified && verified == len(files)`). The digest is taken while writing, never re-read from disk, and on the sender the row is the receiver's report rather than a proof. A mismatched or unreadable digest deletes the .part before the rename and refuses with `CodeHashMismatch`.
- `FileDone` and `OnFileDone` (receiver.go) are what a GUI learns per committed file.
- Whether a sender hashes is decided by `sendFileHashes` (Go, P0-22) and the browser worker constant (P0-21b), so docs say "when the sender provides one"; browser receivers never send `received`, so they never report `verified`.
- The browser's two hash waits (client/lib/transfer/protocol.ts): `hashBoundMs` (size at 10 MB/s plus 30 s), `END_DIGEST_WAIT_MS` (a sender sends `end` without `sha256` once it has waited this long after the last chunk, under a Go receiver's `receiveStallTimeout`) and `POST_END_HASH_WAIT_MS` (a receiver with more files to come keeps a file unverified past it, under the senders' 120 s ack wait; the last file keeps `hashBoundMs`). `TestBrowserHashWaitsFitGoClocks` (cli/engine/transfer/deadlines_test.go) pins the Go side of both. Docs: docs/how-it-works/file-checks.mdx "When a browser runs out of time" (the reader-facing home of both waits), docs/reference/transfer-protocol.mdx (the `end` section and the paragraph under "Timeouts"), docs/reference/limits.mdx "Timeouts" (the SHA-256 row), docs/changelog.mdx (the Web app SHA-256 bullet). The pages that used to repeat the waits (docs/how-it-works/known-limitations.mdx, docs/web-app/receiving.mdx, docs/cli/receive.mdx, docs/desktop/request-links.mdx) now give a clause and link to file-checks; keep them that way.
- Tests: the `endSha256` and `receivedVerified` rows of the parity table (cli/engine/transfer/parity_test.go and client/lib/transfer/parity.test.ts), cli/engine/transfer/hash_test.go.
- Docs: docs/how-it-works/file-checks.mdx (the whole page: who hashes and when, what a mismatch does, "What you see in each app", "When there is no mark", and what the checks do not prove), docs/reference/transfer-protocol.mdx "Integrity" and the `end` and `received` field tables, docs/how-it-works/known-limitations.mdx, docs/how-it-works/encryption.mdx, docs/cli/receive.mdx (the summary example, the `Verified` row paragraph under "Output", and "Files are written as `.part` first"), docs/cli/send.mdx (the Verified row paragraph under the Sent box), docs/desktop/request-links.mdx "The check mark", docs/web-app/request-links.mdx "When the files arrive", docs/web-app/sending.mdx "When it finishes", docs/web-app/receiving.mdx, docs/desktop/sending.mdx, docs/desktop/receiving.mdx, docs/quickstart.mdx (each shows the mark or the row and links to file-checks), CLAUDE.md "Transfer Protocol Versioning", the Store What's new draft.

## Delivery confirmation (the ack's confirms)

- The ack map in `ReceiveFilesWithOptions` (cli/engine/transfer/receiver.go) sets `confirms: true` on every Go receiver's ack; `parseAckConfirms` (sender.go) reads it from the first file's ack, by its exact key and as the literal `true` only, and `SendFilesWithOptions` then runs the delivery wait as `SendOptions.RequireReceived` does: success only on `received`, a refusal returns its `*PeerStoppedError`, and a close returns `ErrClosedBeforeReceived`. Without the field (browser receivers, Go receivers before FT-GO-CONFIRMS step 2) the wait still ends in success at a drained buffer. Additive and optional: `ProtocolVersion` stays.
- `ackConfirmsOf` and `Ack.confirms` (client/lib/transfer/protocol.ts) are the browser twin; the browser sender does not act on it, and the browser receiver's `ackMessage` never sets it (it never sends `received`).
- The wait has no deadline of its own. Its bound is `peer.Connection.Failed` (cli/engine/peer/connection.go: closed once on the failed state, about 30 s after the last packet, never on disconnected), watched by `closeOnFailed` (cli/cmd/floe/connfailed.go) in floe send's `runSend` and by `watchConnFailed` (desktop/requestconn.go) in the desktop's `runSend`. A receiver that keeps its connection alive and never answers holds a send until the person cancels.
- What a person sees: floe send prints the error's own text (`ErrClosedBeforeReceived`, "the connection closed before the receiver confirmed delivery", or the refusal's `PeerStoppedError` sentence); the desktop maps the close through errors.ts's `connection closed` rule to its lost-connection line.
- Tests: the `ackConfirms` rows of the parity table (cli/engine/transfer/parity_test.go and client/lib/transfer/parity.test.ts), `FuzzParseAckConfirms`, the confirms tests and `TestPlainSendWithoutConfirmsEndsAtDrain` in cli/engine/transfer/requirereceived_test.go, the ackConfirmsOf block of client/lib/transfer/protocol.test.ts.
- Docs: docs/reference/transfer-protocol.mdx (the "The end of a batch is a race, not a message." bullet, the `ack` example and fields, the `received` section), docs/troubleshooting.mdx "the connection closed before the receiver confirmed delivery" (the `ErrClosedBeforeReceived` text as its heading), CLAUDE.md "Transfer Protocol Versioning".

## Receiver limits

What Floe Desktop and `floe receive` let a sender's file description ask of the disk, checked before anything is written. A browser receiver has no disk path and applies only the message cap and the display cap.

- cli/engine/transfer/limits.go: `maxPathDepth` and `maxPathUnits`, enforced by `checkPathShape` on every Go receiver, with no option to turn them off. `pathUnits` counts the `.part` staging suffix (`partSuffix`, partial.go) inside `maxPathUnits`, so the length the docs print is the constant less that suffix, and a change to either one moves it. `startsAtDriveOrRoot` is the never-accepted row. `fat32MaxFileSize` and `checkAnnouncedSize` are the FAT and FAT32 row.

- cli/engine/transfer/refusal.go `RefusedError.Error`: the `receive stopped: ...` sentences the docs quote for a path too deep or too long and for a file larger than the save drive can hold.
- desktop/requestlink.go: `requestLabelMax` (the request link's Label, counted in runes).
- Docs: docs/reference/limits.mdx "Transfer size" (the FAT row and the announced-size row) and "Files and paths" (every row), docs/snippets/request-link-limits.mdx (the Label row, the FAT row, and the folder depth and path length row), docs/desktop/request-links.mdx (the **Label** row of the form table), docs/cli/receive.mdx "Paths that are too deep or too long", docs/desktop/receiving.mdx "Paths that are too deep or too long are refused", docs/reference/transfer-protocol.mdx (`metadata` and "How a frame is classified"), docs/troubleshooting.mdx (the path headings under the command line and under Floe Desktop).

## Room seal

- server/server.js: the seal check in `handleJoinRoom` (after the leave-first block: refuse when the room's `roomMeta` record holds two keys and not the joiner's), the key added in `handleSignal` once a signal passes the room and target checks (the create branch starts the set empty and a join never adds to it, so only a peer that has routed a signal counts), and `roomMeta.delete` in `destroyRoom` (the seal lasts exactly as long as the room). The key is `rateKey(ip)` (server/ratekey.js), the same key every per-IP limiter counts under, carried by `createSocketIOPeer` and `createWSPeer`; peers sharing one key are never sealed out, on purpose.
