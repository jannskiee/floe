Someone sent you a Floe link, or a QR code. Open it in any modern browser and the files arrive on
their own. There is nothing to install, no account, and nothing to click to start.

<Info>
A link with `/r/` in it is a request link. It is for sending files to the person who made it, not
for receiving: see [Sending through a request link](/web-app/request-links).
</Info>

## Open the link

Click the link, or point your phone's camera at the QR code. The page joins the sender's room by
itself and starts negotiating the connection. A link made in the web app works for as long as the
sender keeps their page open: see
[How a transfer works](/how-it-works/signaling#code-and-link-lifetime).

### If Floe says "Open in your browser" {#if-floe-says-open-in-your-browser}

Apps like Facebook, Messenger, Instagram, TikTok, Snapchat, LINE, X, and WeChat open links in
their own built-in browser rather than in Chrome or Safari. Those built-in browsers handle file
transfers poorly, so Floe recognizes them and shows this instead of the transfer view.

Those eight are recognized by name, and the screen names the app (it calls X "Twitter"). One more
case is caught by a general check: an Android web view that reports no Chrome version gets the
same screen, worded "This in-app browser". Any other app's built-in browser is not recognized, and
the transfer view opens in it directly.

<Frame caption="What Floe shows when a link is opened inside another app's browser">
  <img src="/images/web/06-in-app-browser.png" style={{ width: "100%", maxWidth: "320px", borderRadius: "12px" }} alt="A full-screen Floe prompt reading Open in your browser, with two numbered steps for reaching Safari, a Copy link to paste in browser button, and a Continue anyway link" />
</Frame>

Follow the two steps, or tap **Copy link to paste in browser** and open it yourself in Chrome,
Safari, Edge, or Firefox. **Continue anyway (some features may not work)** proceeds regardless.

Until you tap **Continue anyway**, the page has not joined the room. That is deliberate: a room
takes exactly one recipient, so an in-app browser cannot silently take that seat and lock the real
browser out.

## While you wait

The card walks through three steps as it gets ready, and offers one choice.

<Frame caption="The receiving card before the first file arrives">
  <img src="/images/web/04-receive-waiting.png" style={{ width: "100%", maxWidth: "520px", borderRadius: "12px" }} alt="The Floe receive card with a green Ready badge, a completed Secure room joined step, an active Waiting for the sender to start step, and a checked Contribute to global stats box" />
</Frame>

The badge at the top right means the same thing it does on the sending side: **Offline** (red) is
no signaling connection, **Ready** (green) is signaling up but the route not yet decided,
**Direct** (green) is device to device, and **Relay** (amber) is through the encrypted relay. It
tracks your own connection, so a green **Ready** does not mean the sender is ready. The ping
readout next to it is shown to senders only.

The transfer starts by itself, usually a couple of seconds after the connection is established.
If it never starts, the sender's side may have stopped it: a browser sender checks the route before
any bytes move and refuses a relayed connection when they turned relay fallback off or queued more
than 2 GB. See [Sending files](/web-app/sending#while-it-transfers).

### Contribute to global stats

Floe's homepage carries a public, all-time count of bytes moved by everyone. When the last file
of a transfer lands, the receiving side adds this transfer's size to that total, and nothing else.
No file names, no contents, nothing identifying, and the report never slows or blocks the
transfer. A transfer that stops before its last file reports nothing.

It is on by default. The checkbox disappears once the first file lands, so decide while you are
waiting.

The total is only ever shown on the homepage. See
[Security and privacy](/security-privacy#aggregate-statistics) for the full data-handling note.

## Saving what arrives

Every file gets its own download button the moment it lands, so you can start saving while the
rest are still coming.

<Frame caption="A finished transfer, with per-file buttons and the two bulk options">
  <img src="/images/web/05-receive-downloads.png" style={{ width: "100%", maxWidth: "520px", borderRadius: "12px" }} alt="The Floe receive card showing Download All and Download ZIP buttons above three completed files, each with its own download button, and the line 3 files received with SHA-256 matched under it" />
</Frame>

On a transfer of two or more files, **Download All** and **Download ZIP** appear as soon as the
second file lands. They hide again while the next file is arriving or being checked and come back
between files, so if they vanish mid-transfer nothing is wrong. Once the transfer finishes they
stay put.

- **Download All** saves each file separately, about one every 300 ms. Your browser may ask you to
  allow multiple downloads.
- **Download ZIP** bundles everything into one archive named `floe_transfer_<timestamp>.zip`. The
  timestamp is milliseconds since the epoch, stamped when the archive finishes building rather
  than when you clicked, so on a large transfer the two differ.

The two differ in more than convenience. A ZIP keeps any folder structure the sender used and
numbers duplicate names inside the archive. Saving files one at a time flattens the structure and
leaves duplicate names to your browser.

A single-file transfer shows only that file's own button, and no bulk options.

**On iOS, use Download ZIP** when there is more than one file. Saving them individually behaves
inconsistently in Safari and in iOS web views. The exception is a very large transfer: zipping
holds every file in memory at once, so if that fails, save them from their own rows instead.

A file that fails a check never reaches the list. Floe discards a file whose size does not match
what the sender announced, or whose SHA-256 does not match when the sender provides one, and the
rest of the transfer stops with it. When every file arrived and every SHA-256 matched, the line
"SHA-256 matched" appears under the list. See [File checks](/how-it-works/file-checks).

Floe does not scan files for malware. A file that passes its checks arrived intact, which does not
make it safe to open and says nothing about who sent it. See
[Known limitations](/how-it-works/known-limitations#floe-does-not-scan-received-files).

Files stay with the browser until you save them, so closing or reloading the tab discards
anything you have not saved.

## The sender has to stay connected

Files stream from the sender's device, so if they close their tab, quit Floe Desktop, or stop the
CLI before the transfer finishes, the connection drops and nothing resumes it.

If **your** connection to Floe's server blips while the two devices are still connecting, the page
rejoins the room by itself. Whether that rescues the transfer depends on the sender. A browser
sender builds a fresh connection. `floe send` and Floe Desktop treat it as you leaving and end the
transfer, and a device that comes back on a different network can be refused. See
[How a transfer works](/how-it-works/signaling#a-room-holds-exactly-two-people). Once the two
devices are connected, a blip in the server connection no longer matters, and the page no longer
rejoins.

What you see when the sender leaves depends on how far things had got:

| When the sender left | What the page shows |
|----------------------|---------------------|
| Before the two devices connected | The second step of the card changes to "The sender is not connected". If a sender in the browser comes back, the transfer starts by itself. See [Troubleshooting](/troubleshooting#the-sender-is-not-connected). |
| After they connected, before any file finished | A red banner, usually "The sender ended the transfer before it finished." or "The sender ended the transfer. Ask them to start it again." See [Troubleshooting](/troubleshooting#the-sender-ended-the-transfer). |
| After at least one file finished, with more still to come | The badge goes back to **Offline**, the progress row goes away, and an amber line under the list says how far the transfer got, such as "Received 1 of 3 files. The transfer ended before the rest arrived." The files that arrived stay listed. See [Troubleshooting](/troubleshooting#the-transfer-ended-before-the-rest-arrived). |

In that last case, save what arrived and ask the sender to send the rest in a new transfer: Floe
[cannot resume](/how-it-works/known-limitations#no-resume) one that stopped. A self-hosted web app
on version 1.11.0 or earlier shows no such line. Its list keeps a green check and a count such as
"1 file received", and a progress row for the file that never finished can stay on screen, so
there the count is the only sign that files are missing.

While a transfer of several files is still running, the same place reads "Received 1 of 3 files.
Waiting for the next file" between files. The green check and a count such as "3 files received"
appear only once every file the sender announced has arrived.

Files that already arrived stay in the list and can still be saved for as long as the page stays
open. To try again in the first two cases, reload the page: that works while a browser sender still
has their page open.

## Receiving in the terminal or the desktop app instead

Both write straight to disk as the bytes arrive and rebuild folder structure, which makes them the
better choice for anything multi-gigabyte. A browser can only take what that browser can hold: see
[Known limitations](/how-it-works/known-limitations#a-browser-receiver-is-limited-by-what-the-browser-can-hold).

```bash Terminal
floe receive "https://www.floe.one/?s=8262e1b4#room=3f2b9c1e-7a4d-4c2e-9b1f-8e6d5c4b3a21"
```

Links made in the browser and in Floe Desktop carry the `?s=` value and links printed by
`floe send` do not. `floe receive` accepts both, and so does the Floe Desktop **Receive** tab. If
the sender gave you a room code instead, pass that. The browser has no field for one.

```bash Terminal
floe receive olive-tiger-castle
```

See [floe receive](/cli/receive) and [Receive files in the desktop app](/desktop/receiving).

## If something goes wrong {#if-the-link-does-not-work}

- "Link Invalid": the link is incomplete, someone else is already connected on it, or it has
  already started connecting from a network other than the one you are on now, which includes
  your own device after it switched networks. See [Troubleshooting](/troubleshooting#link-invalid).
- "The sender is not connected": nobody is on the sending side of the link right now. See
  [Troubleshooting](/troubleshooting#the-sender-is-not-connected).
- The card stays on "Waiting for the sender to start": the two devices are still looking for a
  path, or the sender's side has not started. See
  [Troubleshooting](/troubleshooting#the-transfer-never-starts).
- `Could not connect. Ask the sender to enable "Network Relay" and try again.`: usually a network
  that blocks direct paths, but the sender closing their tab produces it too. See
  [Troubleshooting](/troubleshooting#could-not-connect-ask-the-sender-to-enable-network-relay-and-try-again).
