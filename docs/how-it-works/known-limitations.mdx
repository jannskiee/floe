Floe encrypts every transfer end to end and never puts your files on a server. Both of those
are true and neither is the whole story. This page is the other half: the things Floe does not
do, written plainly, so you can decide whether it fits what you are sending.

Nothing here is a bug report. Each item is a design consequence, and each one says what you can
do about it.

## The signaling server is trusted to introduce you honestly

Two devices agree on encryption keys by exchanging certificate fingerprints, and those
fingerprints travel through the signaling server during setup. The server cannot read your files
and never sees one. But a server that wanted to could hand each side a fingerprint it controls
instead of the other peer's, sit in the middle, and decrypt everything.

This is true of every WebRTC application, not just Floe. It is the reason the next item matters.

**What you can do:** [run your own instance](/self-hosting/overview). A server you operate is a
server you do not have to trust in this sense. On `api.floe.one` you are trusting the same
operator who publishes the client, which is the ordinary situation for any hosted service.

## There is no verification code to compare

The usual defense against the previous item is a short verification code, derived from both
certificate fingerprints, that the two people read to each other over a channel an attacker does
not control. If the codes match, nobody is in the middle.

No client computes or displays that code today. Floe's source still carries the function that
derives it, but nothing calls it. It has been added and removed more than once, and it is not in
the web app, Floe Desktop, or the CLI as they ship now. Until one of them shows it, there is no
way to detect the attack described above from inside Floe.

**What you can do:** for anything where that attack is part of your threat model, self-host, or
encrypt the file yourself before you send it.

## The other person learns your IP address

A direct connection is two devices talking to each other, which means each one knows where the
other is. That is not a leak; it is how any peer-to-peer connection works, and a video call
does the same thing.

With a [request link](/desktop/request-links), that happens as soon as the sender starts the send
and the two devices connect, before the person who made the link accepts or declines. Declining
does not take it back.

**What you can do:** Floe Desktop has a [Hide my IP address](/desktop/settings#hide-my-ip-address)
switch that forces every transfer through the relay, so the other side sees the relay's address
instead of yours, and the CLI's `--relay-only` flag does the same. The web app's Send page has no
equivalent, but the page a sender opens from a request link has its own
**Hide my IP (relay only, 2 GB per drop)** checkbox. The trade is speed and the 2 GB session cap.

## The relay sees more than the signaling server does

When a direct path is impossible, traffic goes through a TURN relay. The relay cannot read
anything: the data is encrypted before it arrives and decrypted only on the recipient's device.

But the relay is an endpoint that both peers connect to, so it observes both IP addresses and
the timing and size of what it forwards. On `floe.one` that relay is Cloudflare's Realtime TURN
network, which is infrastructure Floe does not own, and its operator may log that metadata for
its own security purposes.

**What you can do:** stay on a direct connection where you can, or self-host with
[your own coturn relay](/self-hosting/turn-relay).

## A browser receiver is limited by what the browser can hold

The web app keeps every file it receives inside the browser until you leave the page, so that you
can still save it. What counts is therefore the size of the whole transfer, not of its largest
file, and how much fits depends on the browser.

- **Chrome, Edge, and other Chromium browsers, in a normal window:** the tab holds no more than
  about 16 MB of a file at a time. The browser keeps some of what has arrived in memory (about 2 GB
  on a computer) and moves the rest into temporary files of its own on disk, up to a limit it sets
  from the size of the disk. Past that limit the transfer stops and says
  [the browser ran out of memory](/troubleshooting#this-browser-ran-out-of-memory).
- **A private or Incognito window in those browsers:** nothing goes to disk, so everything received
  in private windows shares the memory part alone, about 2 GB on a computer and much less on a
  phone. Past that the transfer stops the same way.
- **Firefox, Safari, and every browser on iPhone and iPad:** every file is held in memory. A large
  enough transfer runs the tab out of memory, and on a phone that ceiling arrives sooner than you
  would like.

When a transfer stops this way, the files that had already arrived stay in the list and can still
be saved.

Zipping compounds it in every browser: **Download ZIP** reads every file back into the tab at once
before it writes the archive.

**What you can do:** receive multi-gigabyte transfers with [Floe Desktop](/desktop/receiving) or
the [CLI](/cli/receive), which write straight to disk and have no such ceiling. In the browser,
use a normal Chrome or Edge window, and save files one at a time rather than zipping when the
total is large.

## The SHA-256 check covers the transfer, not your disk afterward

Floe checks every file it receives against the size the sender announced and, when the sender
provides one, against the sender's SHA-256 of the file, and it deletes a file that fails either.
[File checks](/how-it-works/file-checks) has the whole account.

Two things the check does not do. It covers the file as it arrived, so it cannot notice damage
that happens on your disk afterward: Floe Desktop and `floe receive` take the SHA-256 while they
write the file and never read it back, and the web app checks the copy it holds, before your
browser saves it. And a file that comes without a SHA-256, or whose check did not finish
[in the time allowed](/how-it-works/file-checks#when-a-browser-runs-out-of-time), is checked against its
size and nothing more. That file is kept, and no green check mark or `SHA-256 matched` line appears.

**What you can do:** compare hashes yourself when you need proof about the file as it sits on
disk. `sha256sum` on Linux,
`shasum -a 256` on macOS, `Get-FileHash` on Windows.

## Windows cannot keep two names that differ only by a reserved character

Windows refuses `< > : " | ? *` in a file name, so Floe Desktop and `floe receive` on Windows
replace each of them with `_` before writing. Names that were distinct on the sending machine can
then land on the same name. A Linux folder holding `report:v1.pdf` and `report?v1.pdf`
arrives as `report_v1.pdf` and `report_v1 (1).pdf`, and nothing on disk says which was
which. The numbered suffix follows the order the files arrived in, which is the order they
were sent.

Nothing is overwritten and nothing is lost. The receiver never replaces an existing file, so
the second one is saved beside the first rather than on top of it. `floe receive` on macOS and
Linux keeps both names as they were sent, because those characters are legal there. The web app
replaces the same characters on every operating system, because a ZIP it builds may be opened on
Windows.

**What you can do:** if the distinction matters, rename the files before sending, or send to
`floe receive` on macOS or Linux. The progress line of `floe receive` and the History in Floe
Desktop both show the name that was actually written, so you can always tell what landed where.

## Very deep or very long paths are refused

Before they write a file, Floe Desktop and `floe receive` refuse one whose path inside the
transfer is too deep or too long, or that starts at a drive or a root. The receive stops there and
tells the sender why. Files saved before it are kept, and no setting or flag turns the limits off.
The numbers are in [Limits](/reference/limits#files-and-paths).

**What you can do:** zip deeply nested folders before sending them. See
[what the desktop app shows](/desktop/receiving#paths-too-deep-or-too-long) and
[what `floe receive` prints](/cli/receive#paths-too-deep-or-too-long).

## Floe does not scan received files

Floe does not scan received files for malware. On Windows, Floe Desktop and `floe receive` mark each
file as downloaded, the way a browser does, so SmartScreen and Office Protected View treat it like any
download. The mark needs a drive that can keep it, and not every drive does. See
[Received files are marked as downloads](/desktop/receiving#received-files-are-marked-as-downloads).

**What you can do:** open files you did not expect with the same care as any download, and save
to an NTFS drive when the mark matters. A drop through a request link also renames file types that
File Explorer opens by itself; see [Renamed files](/desktop/request-links#renamed-files).

## Windows decides where a notification appears {#notifications}

Floe Desktop sends standard Windows notifications, and Windows decides how they show: on which screen,
in which corner, for how long, and whether Focus or Do Not Disturb hides them. Floe cannot pick a screen
or a corner. A notification also stays in Notification Center after the request it announced has ended, or
after you have answered it, until you clear it. Clicking a notification is not a way back to the request yet: switch to Floe to answer it.

**What you can do:** open Windows' notification settings, where Floe has its own entry (Floe Desktop for the Microsoft Store build), with **Open** under
[Windows notification settings](/desktop/settings#windows-notification-settings) in Settings. Turn
notifications off there, or in Floe, if you would rather not have them. A request still flashes the taskbar button, the window title
reads `(1) Floe`, and a notice appears inside Floe. See
[With notifications off](/desktop/settings#notifications-off).

## A request link works only while your PC is on

A request link is a live transfer, not a mailbox. Files move only while Floe Desktop is open on
your PC and the PC is awake and online, and only while the sender's page, or their `floe send --to`,
stays open. There is no resume: if the connection drops, the file that was moving starts over
through a new link. A drop that runs for hours can also be cut short by Windows restarting for
updates outside your active hours.

**What you can do:** keep the PC plugged in and awake for a long drop, and set Windows Update's
active hours to cover it. A sender in a browser keeps the tab in front, and pins it for a long
drop. See [Request links](/desktop/request-links).

## The public counter is a vanity metric

The total on the homepage is fed by receivers reporting a byte count after a transfer. It is
protected by a per-address rate limit and a per-report size cap, and nothing else. Anyone can post
a plausible number to it.

It is an honest best-effort figure, not an audited one, and it is deliberately built that way:
adding real integrity would mean identifying the reporter, which is exactly what the counter
avoids. It carries no file names, no per-transfer records, and no link to anyone. See
[Aggregate statistics](/security-privacy#aggregate-statistics).

## A self-hosted server runs as a single process

Rooms, room codes, request-link reservations, and the rate limiters all live in one process's
memory. Running two replicas
behind a load balancer does not scale Floe out; it silently breaks pairing, because the two
peers can land on different replicas and never see each other.

**What you can do:** run one instance. A single small server handles a lot, since file data
never passes through it. If you need redundancy, use a failover pair rather than a load-balanced
set, and accept that the switch loses every room and room code the old instance held, as a
[restart](/self-hosting/operations#common-commands) does.

## Reporting something that is not on this list

If you find a security issue in Floe, report it privately through
[GitHub Security Advisories](https://github.com/jannskiee/floe/security/advisories/new) or the
contact in [SECURITY.md](https://github.com/jannskiee/floe/blob/main/SECURITY.md). Please do not
open a public issue before there is a fix.
