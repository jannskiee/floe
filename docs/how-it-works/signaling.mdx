Floe never moves your file. It introduces two devices, they build a connection between
themselves, and the file crosses that connection, not the server. Once both devices are there,
the server's part takes a few seconds.

That is the entire idea. The rest of this page is what those few seconds consist of.

## Step by step

<Steps>
  <Step title="You create a transfer">
    Your device makes up a random room id and joins that room. You share a link containing it, or
    a three-word room code that maps to it.
  </Step>
  <Step title="They join the same room">
    The server now has two devices in one room, and tells the first one that someone arrived.
  </Step>
  <Step title="The two devices introduce themselves">
    They pass an offer, an answer, and a list of network addresses through the server, each
    trying to find a path to the other.
  </Step>
  <Step title="The connection opens and the server drops out">
    Every byte of the file travels over that connection. None of it goes back through the server.
  </Step>
</Steps>

Steps 1 to 3 all pass through the server. Step 4 does not.

A [request link](/desktop/request-links) runs the same steps with the roles the other way around:
the Floe Desktop that made the link is in the room first and receives, and the person sending joins
when they press the send button on the link's page or run `floe send --to`.

On most networks the path found in step 3 is direct, device to device. When a firewall or a
carrier's network makes that impossible, the connection runs through an encrypted relay instead.
See [Direct connections](/how-it-works/direct-connection) and
[Relay fallback](/how-it-works/relay-connection).

## What the server does

- Puts two devices in a room and assigns roles. For a room code or a share link, the first to join
  sends and the second receives. A [request link](/desktop/request-links) keeps the receiving seat
  for the Floe Desktop that made it, and the person sending joins second.
- Passes the connection-setup messages between them.
- Hands out time-limited credentials for the relay, when one is configured.
- Turns a room id into a three-word room code when `floe send` or Floe Desktop asks for one, and
  back into the room id for a receiver who types it, for 10 minutes at most. See
  [How long a code and a link last](/how-it-works/signaling#code-and-link-lifetime).
- Adds the size of a finished transfer to one public running total, if the receiving side is
  willing. That is a single shared number, and every client can switch it off. See
  [Security and privacy](/security-privacy#aggregate-statistics).

## What the server never does

- Touch file data. Not in transit, not at rest, not in any form.
- Store file names, contents, or a record of what you sent or to whom.
- Keep a room once its session is over. The room is dropped when the last connection to it
  closes, and its room code is dropped with it. While a code lasts, it maps to nothing but a
  random room id. What the server holds about the devices themselves, and for how long, is in
  [Security and privacy](/security-privacy).
- Connect the byte total to you. It is one number with no per-user or per-transfer rows behind it.

A request link is the one room that outlives its connections. The server holds it for the Floe
Desktop that made it, with a hash of that app's secret token and never the token itself, for about
10 minutes after the app disconnects, so the app can come back to it. When a link that someone
connected through is closed, the server remembers for a day that it was used. For any other link
it remembers the link's room id and end time until a day after it ends, so a late visitor can be
told it ended. It keeps nothing else about either.

## A room holds exactly two people

The room is the transfer. It takes one sender and one receiver, and a third device that tries to
join is turned away: the web app shows **Link Invalid**, while `floe receive` and Floe Desktop say
`room is full (someone else may already be receiving)`.

The seat frees again once that device disconnects and the server notices, which takes up to about
a minute if the drop was not a clean one. Whether the transfer survives that gap depends on who is
sending: the web app holds its room open for the receiver to come back from the same network, while
`floe send` and Floe Desktop end the transfer as soon as the receiving side goes.

A freed seat does not let just anyone in. Once devices on two different networks have each sent a
connection-setup message through a room, as a sender and a receiver do the moment they start
connecting, a device on a third network is turned away as if the room were full, for as long as
the room exists. Joining alone does not count, so a sender whose network changes while it waits for
its receiver is not counted twice. Devices that share one network address (for IPv6, one /64)
count as one, so two people behind the same router are not told apart.

The same rule turns away one of the two people themselves if their network changes after they
have started connecting, for example from Wi-Fi to mobile data. They need a new link. See
[a device that changed networks is refused](/troubleshooting#a-device-that-changed-networks-is-refused).

A [request link](/desktop/request-links) differs in one way: it is used up. Once someone connects
through it, the room seals, and nobody else can take the seat while their request or their drop
lasts. When the drop ends, a later sender is told the link has already been used. A request that
is declined or not answered in time does not use it up: the link can wait again for the next
sender.

For a second recipient, start a second transfer.

### How long a code and a link last {#code-and-link-lifetime}

A room code is the three words that `floe send` and Floe Desktop show beside their link. The web
app's Send page makes a link and no code. A code works for 10 minutes at most, counted from the
moment it is made, and the server retires it sooner when any of these happens first:

| What happens | What it does to the code |
| --- | --- |
| A receiver joins the room | Both seats are taken, so the code stops working at once. A third device that types it is told the code was not found, not that the room is full. |
| The sender leaves before anyone joins | The room is gone, and its code goes with it. |
| The same room is given a new code | A room has one working code at a time, so the earlier one stops. |
| The server restarts | Codes are kept in memory only, so every code is forgotten. |

Looking a code up does not use it up. A receiver whose attempt fails before it takes its seat, for
example because `--relay-only` found no relay on the server, can try the same code again.

Nothing extends the 10 minutes. A sender who is still waiting after that can be reached only
through the link. A code that has stopped working looks the same whatever retired it: `floe receive`
prints
[`code "olive-tiger-castle" not found or expired (codes expire after 10 minutes)`](/troubleshooting#code-olive-tiger-castle-not-found-or-expired-codes-expire-after-10-minutes),
and Floe Desktop shows
"[That code wasn't recognized](/troubleshooting#that-code-was-not-recognized)".

A share link has no clock of its own. It carries the room id, so it works for as long as its
sender is still in the room:

- A link from the web app's Send page works while the sender's tab stays open and connected.
- A link from `floe send` or Floe Desktop works until that send finishes, fails, or is canceled.
  Neither sets a limit on how long it waits for a receiver.

The server does not use a link up when it is opened. A device that opens it while a receiver is
connected is turned away because the second seat is taken, not because the link was opened before.
A link from `floe send` or Floe Desktop still serves one receiver only: that send ends when its
receiver leaves, even a receiver that only opened the link and closed it again. Once the sender has
left, the link leads to an empty room: the web app waits for a sender who is not coming, and
`floe receive` and Floe Desktop say
[`this code is no longer active; ask for a new one`](/troubleshooting#this-code-is-no-longer-active-ask-for-a-new-one).

A request link follows its own rules: its end time is chosen when it is made, and one accepted
drop uses it up. See [how a request link ends](/desktop/request-links#how-a-link-ends).
