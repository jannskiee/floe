This page runs the signaling server and the web client straight from a clone of the repository, with Node.js and no containers. It is for hosts where Docker is not an option, and it leaves you with two long-lived processes to supervise and a checkout to keep up to date. The variables in [Configuration](/self-hosting/configuration) apply here too, and the rows that behave differently on a direct run say so.

## Prerequisites

- **Node.js 22 or later**, for both processes. The client sets that floor: it pins pnpm 11, which needs Node.js 22, and Next.js 16 asks for 20.9 or later. The signaling server's runtime dependencies ask only for Node.js 18, and its `package.json` has no `engines` field, so nothing stops you from starting it on something older. The oldest version anything tests is Node.js 20, which CI runs the server's tests on. CI builds the client on Node.js 22, and both published images run Node.js 24.
- **pnpm 11**, for the client. `client/package.json` pins `pnpm@11.1.2`. Install that version, for example with `npm install -g pnpm@11.1.2`, which is what the image build does.
- **Git**, to clone the repository and to update it later.

The optional CLI build below also needs Go. See [Install the CLI](/cli/installation#build-from-source).

## Running each component

The signaling server and the web client are two long-lived processes, so each
needs its own terminal, or a process supervisor such as pm2 or systemd.

<Steps>
  <Step title="Clone the repository">
    ```bash Terminal
    git clone https://github.com/jannskiee/floe.git
    cd floe
    ```

    Run every later block from this folder, the repository root.
  </Step>
  <Step title="Copy the environment files">
    ```bash Terminal
    cp server/.env.example server/.env
    cp client/.env.example client/.env.local
    ```

    The copies work as they are while the browser is on the same machine. Before you build for anyone else, set the values under [Environment variables](#environment-variables): two of them are compiled into the client.
  </Step>
  <Step title="Start the signaling server">
    ```bash Terminal
    # Signaling server (Node.js). Stays in the foreground.
    cd server
    npm install
    npm start
    ```

    It listens on port 3001, and the server itself logs nothing when it starts. Check it from another terminal with `curl -s http://localhost:3001/health`.
  </Step>
  <Step title="Build and start the web client">
    ```bash Terminal
    # Web client (Next.js). Stays in the foreground.
    cd client
    pnpm install
    pnpm build
    pnpm start
    ```

    Then open [http://localhost:3000](http://localhost:3000).
  </Step>
</Steps>

Serve the client from a production build: `pnpm build`, then `pnpm start`. `pnpm dev` is for development only, and it always dials `http://localhost:3001` unless `NEXT_PUBLIC_SOCKET_URL` is set, whatever `SOCKET_URL` says.

To try the instance from a terminal, build the CLI and point it at the signaling server:

```bash Terminal
# CLI (optional, for local testing against your server)
cd cli
go build ./cmd/floe
./floe send photo.jpg --server http://localhost:3001
```

For a development setup with live reload, see [CONTRIBUTING.md](https://github.com/jannskiee/floe/blob/main/CONTRIBUTING.md#development-setup).

## Environment variables

Both example files are written for one machine. Before the instance serves anyone else, change these:

| File | Variable | Set it to |
|------|----------|-----------|
| `server/.env` | `CLIENT_URL` | The exact origin people open the web client at, for example `https://floe.example.com`. |
| `server/.env` | `TRUSTED_PROXY_COUNT` | The number of reverse proxies in front of the server. The example says `1`. Use `0` when the server is reached directly, or clients can forge the address the rate limits count. |
| `client/.env.local` | `NEXT_PUBLIC_SOCKET_URL` | The signaling server's address as browsers reach it, for example `https://api.your-domain.com`. |
| `client/.env.local` | `NEXT_PUBLIC_SITE_URL` | Your own public address. |

<Warning>
  Set `NEXT_PUBLIC_SITE_URL` to your own address before you run `pnpm build`. The example value, `http://localhost:3000`, is written into every canonical link, share preview, and sitemap entry. With the line removed or left empty, a build you run yourself falls back to `https://www.floe.one`, so your instance advertises floe.one as its canonical site. Only a build through the official Dockerfile leaves the address out instead, because a flag set there switches that on. See [Container images](/self-hosting/images#share-previews-and-canonical-links).
</Warning>

Both client values are inlined when the client is built, so changing either one later means another `pnpm build`.

To change the signaling address without rebuilding, remove `NEXT_PUBLIC_SOCKET_URL` from `client/.env.local` before you build, and set the unprefixed `SOCKET_URL` in the environment of the process that runs `pnpm start` instead; the browser then reads it per request from `/api/config`. See [How the client finds the server](/self-hosting/build-time-url). Leave both empty when the client and the signaling server share one origin behind a reverse proxy.

The server reads `.env` from the folder it is started in, so start it from `server/`, or point your supervisor's working directory there. A variable already set in the process environment wins over the file.

Keep `NODE_ENV=production`, which `server/.env.example` already sets. It is what the published image runs, where Docker sets it for you, so a direct Node run with that line matches the image. Nothing leaks without it: Floe registers its own final error handler, which returns a generic JSON error at every setting.

[Request links](/desktop/request-links) stay off until `POLICY_FILE` in `server/.env` names a policy file. See [Turn on request links](/self-hosting/request-links#without-docker).

## Updating an existing deployment

The Docker instructions in [Operations](/self-hosting/operations) assume there is no repository to keep in sync. Running directly with Node means there is, so pull, reinstall, then restart:

```bash Terminal
cd /path/to/floe
git pull

# Signaling server
cd server
npm ci --omit=dev

# Web client: a compiled build, so it has to be rebuilt
cd ../client
pnpm install --frozen-lockfile
pnpm build
```

Then restart both processes with whatever supervises them (`pm2 restart <name>`, `systemctl restart <unit>`, or your own runner). `pnpm start` serves whatever `pnpm build` last produced, so skipping the client rebuild leaves the old client running with nothing to indicate it is stale. A server restart forgets every room and room code, so pick a quiet moment; see [Operations](/self-hosting/operations#common-commands).

<Warning>
  Reinstall before you restart, and do not skip it. A dependency update that only moves a lockfile changes no source file, so a restart on its own re-executes the same `node_modules` and the update silently does not take effect. The process comes back healthy and the old version is still running.
</Warning>

Confirm the restart landed by checking that uptime reset:

```bash Terminal
curl -s http://localhost:3001/health
```

To confirm a specific dependency actually moved, read the installed version rather than trusting the restart:

```bash Terminal
npm --prefix server ls <package-name>
```

## If something goes wrong

- The server prints nothing after `npm start`: that is expected. See [The server logs nothing at all](/troubleshooting#the-server-logs-nothing-at-all).
- The page loads and the badge stays on **Offline**: see [The browser cannot connect to my signaling server](/troubleshooting#the-browser-cannot-connect-to-my-signaling-server).
- The server answers `403` to the browser: `CLIENT_URL` does not match the page's origin. See [Browser requests are blocked, and the server answers HTTP 403](/troubleshooting#browser-requests-are-blocked-and-the-server-answers-http-403).
