## Common commands

```bash Terminal
docker compose logs -f                  # tail logs for all services
docker compose ps                       # check container status and health
docker compose down                     # stop and remove the stack
docker compose restart server           # restart only the signaling server
```

**Restarting the server is not free.** Rooms and room codes live in that process's memory, so a
restart forgets every short code. A CLI or Floe Desktop sender still waiting for its receiver stops
and has to start again; one in the web app reconnects on its own within a few seconds and keeps its
link. A transfer that is already running keeps going, because file data never passes through the
server, except between two browsers: the shutdown tells one that the other has left, and the
transfer stops. One that was still connecting may need another try. There is no draining and no
warning. Pick a quiet moment.

A [request link](/desktop/request-links) that is waiting for a sender comes back on its own. The
server forgets it too, but a Floe Desktop that is still open reconnects and makes the same link
again, so the person it was sent to can still use it. What a restart does lose is the mark on a link
that was used, or that ended before anyone used it: a later sender sees "Their computer is not
connected right now" instead of "This link has already been used" or "This link has ended".

The client also waits on the server: Compose starts it only once the server reports healthy. If
the server never gets there, you do not get a web app that cannot connect, you get no web app at
all.

## Update to the latest code

```bash Terminal
docker compose pull
docker compose up -d
```

That pulls the newest [published images](/self-hosting/images) and restarts. Nothing is built locally, so there is no repository to keep in sync.

If you run the optional coturn relay, add its profile to both commands or Compose skips the service entirely, so a new coturn image is never pulled and a stopped relay is never restarted:

```bash Terminal
docker compose --profile turn pull
docker compose --profile turn up -d
```

Setting `COMPOSE_PROFILES=turn` in your `.env` applies it to every later `docker compose` command.

Changing `NEXT_PUBLIC_SOCKET_URL` needs only `docker compose up -d`; the client reads it at runtime. See [How the client finds the server](/self-hosting/build-time-url). `NEXT_PUBLIC_SITE_URL` is the exception: it is written into the page at build time, so the published image omits those tags entirely rather than pointing them at somebody else's domain. See [Container images](/self-hosting/images) if you want your own.

## The server logs very little

Worth knowing before you go looking. The signaling server has no access log, no request log, and
no startup banner, not even a line saying which port it bound. `docker compose logs server` on a
healthy instance is usually empty, and that is expected rather than a symptom.

A request its error handler refuses gets one fixed line and no stack trace:
`Refused a request with 403.` for a browser request from an origin it does not allow, or the same
line with another status under 500, such as `400` for malformed JSON or `413` for a body over the
size limit. The line carries the status and nothing else, never the origin, the path, or any of the
request's text. An occasional one is some page or client sending a bad request, not a fault. If
`403` lines show up each time someone uses your own web client, check `CLIENT_URL`.

It writes a stack trace in exactly three cases: when a server-side error (a `5xx`) reaches its
error handler, when it cannot bind its port at startup (prefixed `HTTP server error:`, after which
it exits), and when an unexpected exception reaches the process-level backstop. The last kind is
prefixed `Unhandled error` and means the server caught something it did not anticipate and kept
serving rather than exiting, so the transfers in progress survived. It is worth reporting. To
confirm the server is alive, or that a restart actually landed, use the health endpoint below
rather than the logs.

`docker compose ps` is a similar case: **the client image ships no healthcheck**, so it never
reports a health state. Only the server does.

On `SIGTERM` or `SIGINT` the server closes every WebSocket with code `1001` and the reason
`Server shutting down`, stops accepting connections, and exits. If something is still holding it
open ten seconds later it exits anyway.

## Health endpoints

The signaling server exposes two status endpoints:

| Endpoint | Purpose | Response |
|----------|---------|---------|
| `GET /health` | Liveness check | `{ "status": "healthy", "uptime": <seconds>, "features": [...] }` |
| `GET /` | Status and timestamp | `{ "status": "ok", "timestamp": "..." }` |

Point a monitor at `/health`. It is the only one of the two that survives a
[one-domain deployment](/self-hosting/reverse-proxy), where `/` belongs to the
web client and returns a page rather than JSON. `GET /` on the signaling server
is reachable only when you address the server directly, on `:3001` or on its own
subdomain.

`features` is `["request-1"]` while request links are on and `[]` while they are off. See
[the HTTP API](/reference/http-api).

## Request links {#request-links}

A self-hosted server offers [request links](/desktop/request-links) only when its policy file turns
them on. With no policy file they are off, and codes and share links work as usual.

<Steps>
  <Step title="Create the policy file">
    Next to `docker-compose.yml`:

    ```bash Terminal
    mkdir -p policy
    echo '{"requestLinks": true}' > policy/policy.json
    ```
  </Step>
  <Step title="Mount the folder and name the file">
    In `docker-compose.yml`, uncomment the server's `volumes` example:

    ```yaml docker-compose.yml
    volumes:
      - ./policy:/app/policy:ro
    ```

    Then, in `.env`:

    ```dotenv .env
    POLICY_FILE=/app/policy/policy.json
    ```

    Mount the folder, not the file. An edit puts a new file in place of the old one, and a mount of
    the single file keeps showing the old one.
  </Step>
  <Step title="Recreate the server and check">
    ```bash Terminal
    docker compose up -d
    curl http://localhost:3001/health
    ```

    The answer lists `"features":["request-1"]`, and the server's log has one line,
    `request links: on`.
  </Step>
</Steps>

### Turn request links on or off later {#turn-request-links-on-or-off}

The server re-reads the file every 60 seconds, so no restart is needed. Write the new content to a
temporary file and rename it over the old one, rather than editing the file in place, so the server
never reads a half-written file:

```bash Terminal
echo '{"requestLinks": false}' > policy/policy.json.tmp
mv policy/policy.json.tmp policy/policy.json
```

Then wait up to 60 seconds. The log says `request links: off` (or `request links: on`), and
`/health` follows.

Turning request links off ends every link that is waiting for a sender, and Floe Desktop shows
"Request links are off on this server". A drop that is already under way is left to finish.

The server reads the file this way:

- Only `true`, the JSON boolean, turns request links on. `"true"` in quotes, any other value, and a
  missing `requestLinks` key all mean off. Other keys are ignored.
- A file that cannot be read, is not a JSON object, or is larger than 64 KB changes nothing: the
  server keeps its last good setting and logs `policy file unreadable, keeping previous policy`
  once, until the file reads cleanly again.
- A missing file means off, and while a set `POLICY_FILE` stays missing the server logs `policy file not found, request links off` once.
- UTF-8 works, and so does the UTF-16 that Windows PowerShell writes by default.

### Keep the client and server on one version {#matching-versions}

The page a sender opens comes from the web client, not from the signaling server, so run the two
images at the same version. Compose does that by default, because `FLOE_IMAGE_TAG` picks both. An
older client in front of a newer server lets Floe Desktop make links whose page does not exist.

Floe Desktop builds the link from its **Share link address** setting, or from the server address
when that is blank. See [Self-hosted servers](/desktop/request-links#self-hosted-servers). How the
server holds a request link's room is described in
[the architecture reference](/reference/architecture#request-rooms).

The page a sender opens carries **Report this link** on every server, and on yours it still starts
an email to Floe's maintainers, who cannot turn off or trace another server's links. Tell the people
you share links with how to reach you instead.
