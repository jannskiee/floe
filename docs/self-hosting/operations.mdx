Reference for a Floe instance that is already running under [Docker Compose](/glossary#docker-compose):
the commands you will reach for, what a restart costs, how to update, what the server logs, and
which endpoint to monitor.

## The short version {#the-short-version}

`docker compose pull` and `docker compose up -d` update the instance. Every restart forgets the
room codes people are waiting on, so pick a quiet moment. Point a monitor at `/health`, and expect
the server's log to be nearly empty.

## Common commands

```bash Terminal
docker compose logs -f                  # tail logs for all services
docker compose ps                       # check container status and health
docker compose down                     # stop and remove the stack
docker compose restart server           # restart only the signaling server
```

Every service in the compose file is set to `restart: unless-stopped`. The server, the client, and
coturn come back by themselves after a crash, and when the host starts again after a reboot. They
stay down only after `docker compose stop` or `docker compose down`. Docker does not restart a
server that is only unhealthy.

<Warning>
  Restarting the server is not free. Every [room](/glossary#room) and [room code](/glossary#room-code)
  lives in that process's memory, so a restart forgets every room code, and a [CLI](/glossary#cli)
  or Floe Desktop sender still waiting for its receiver stops and has to start again. There is no
  draining and no warning. Pick a quiet moment.
</Warning>

What a restart does to each person using the instance:

| Who | What a restart does |
|---|---|
| A sender in the web app, waiting for the other person | It reconnects on its own within a few seconds and keeps its link. |
| A sender in the CLI or Floe Desktop, waiting for the other person | It stops, and has to start again with a new code. |
| Two people whose transfer is already running | Nothing: file data never passes through the server. A transfer that was still connecting may need another try. |
| The owner of a [request link](/glossary#request-link) that waits for a sender | The link comes back on its own: a Floe Desktop that is still open reconnects and makes the same link again. |
| A sender who opens a link that was used, or that ended before anyone used it | They see "Their computer is not connected right now" instead of "This link has already been used" or "This link has ended", because the server forgot the mark. |

A web client older than 1.11.0 is the exception to the third row: its transfer stops when the
server tells the page that the other side has left, as a shutdown can.

The client also waits on the server: Compose starts it only once the server reports healthy. If
the server never gets there, you do not get a web app that cannot connect, you get no web app at
all.

## Update to the latest code

```bash Terminal
docker compose pull
docker compose up -d
```

That pulls the image tag you run, which is `latest` unless `FLOE_IMAGE_TAG` in `.env` names another, and restarts on it. See [Container images](/self-hosting/images) for the tags. Nothing is built locally, so there is no repository to keep in sync. If you pinned a version, change `FLOE_IMAGE_TAG` first, or the pull has nothing new to fetch. An update is a restart, with the cost described above.

Pulling never changes your `docker-compose.yml`, though, and a setting that a release adds reaches the containers only through that file. A copy from 1.11.0 or earlier passes neither `TURN_TLS` nor `REQUEST_REPORT_EMAIL`, both new in 1.11.1, and a copy from 1.11.1 or earlier does not pass `MAX_SOCKETS_PER_IP`, which is newer, so setting any of them in `.env` does nothing. To use one, download the current file from [GitHub](https://github.com/jannskiee/floe/blob/main/docker-compose.yml) and copy your own changes across.

If you run the optional coturn [relay](/glossary#relay), add its profile to both commands or Compose skips the service entirely, so a stopped relay is never restarted:

```bash Terminal
docker compose --profile turn pull
docker compose --profile turn up -d
```

Setting `COMPOSE_PROFILES=turn` in your `.env` applies it to every later `docker compose` command. The compose file pins coturn, Floe's optional [TURN](/glossary#turn) server, to `coturn/coturn:4.15`, so the pull refreshes that version only; see [TURN relay](/self-hosting/turn-relay#if-you-run-coturn).

Changing `NEXT_PUBLIC_SOCKET_URL` needs only `docker compose up -d`, because the client reads it at runtime. See [How the client finds the server](/self-hosting/build-time-url). `NEXT_PUBLIC_SITE_URL` is the exception: it is written into the page at build time, so the published image cannot carry it. That image leaves your domain out of share previews and the sitemap rather than pointing them at somebody else's. See [Container images](/self-hosting/images#share-previews-and-canonical-links) for what the image emits and how to build your own.

### Moving to 1.11.0 {#moving-to-1-11-0}

Version 1.11.0 changed what a [self-hosted](/glossary#self-hosted) instance needs. Go through these
five points once, when you move up from an older version:

- **Pass the `Host` header through your proxy.** This matters only when the CLI or Floe Desktop
  reaches the server through a [reverse proxy](/glossary#reverse-proxy) on a hostname that is not
  exactly your `CLIENT_URL`, as on the [two-hostname layout](/self-hosting/production). From 1.11.0
  the server checks the origin of every [WebSocket](/glossary#websocket), and it lets those two
  clients in by comparing their `Origin` with the hostname in `Host`. A proxy that rewrites `Host`
  to its upstream address gets them refused with a `403`. Browsers on your `CLIENT_URL`, a
  [one-domain deployment](/self-hosting/reverse-proxy), and a server reached without a proxy are
  not affected.
- **Take the current `docker-compose.yml`.** Pulling images never changes your copy. One from
  before v1.11.0 passes neither `POLICY_FILE` nor `MAX_FAILED_CODE_RESOLVES` to the server, so
  setting them in `.env` does nothing. Download the one on
  [GitHub](https://github.com/jannskiee/floe/blob/main/docker-compose.yml) and copy your own
  changes across. You need it before you turn on [request links](/self-hosting/request-links),
  which stay off until you do.
- **Keep the client and the server on one version.** The page a request-link sender opens is part
  of the web client, so a 1.11.0 server behind an older client hands out links to a page that does
  not exist. Compose picks both images with `FLOE_IMAGE_TAG`; if you pinned `1.10.11`, move it to
  `1.11.4` or the newest tag in [Container images](/self-hosting/images#tags). See
  [Keep the client and server on one version](/self-hosting/request-links#matching-versions).
- **Know the new failed-lookup setting.** Each address gets 10 failed room-code lookups in 60
  seconds, and the new optional `MAX_FAILED_CODE_RESOLVES` changes that number. A lookup that finds
  a code costs nothing, but once an address has spent its 10, every lookup from it answers `429`
  until the misses age out. Raise it only if many people behind one address mistype codes. See
  [Configuration](/self-hosting/configuration).
- **Expect IPv6 clients to share limits by /64.** Every per-address limit now counts an IPv6 client
  by its /64 instead of its single address, so everyone inside one /64 shares one budget, as
  everyone behind one IPv4 address always has. If a whole office or campus sits in one /64, raise
  `MAX_CONNECTIONS_PER_IP` and the other limits to fit.

One change needs nothing from you. From 1.11.0 the server turns a third network away from a room
once devices on two networks have started connecting through it. An older server lets a device
from any network into a free place. See
[A room holds exactly two people](/how-it-works/signaling#a-room-holds-exactly-two-people).

The [Changelog](/changelog) lists everything else that changed in v1.11.0.

## The server logs very little

Worth knowing before you go looking. The [signaling server](/glossary#signaling-server) has no
access log, no request log, and no startup banner, not even a line saying which port it bound.
`docker compose logs server` on a healthy instance is usually empty, or holds the one line
`request links: on`, and that is expected rather than a symptom. A server run with Node directly
and no `TRUSTED_PROXY_COUNT` writes one line about that at startup, and so does a server given a
word or a negative number for it; see the table.

It never logs an accepted connection, a room, a code, a rate-limit refusal, or a request-link event,
and no line is built from a client's address. These are all the lines it can write:

| Message | What it means | What to do |
|---|---|---|
| `request links: on` or `request links: off` | The request-link setting took effect: at startup when the policy file says on, and afterward whenever it changes. A server that starts with request links off writes neither. | Nothing. See [Turn on request links](/self-hosting/request-links). |
| `policy file not found, request links off` | `POLICY_FILE` is set, but no file is at that path. Written once for as long as the file stays missing. | Check the volume mount and the path. |
| `policy file unreadable, keeping previous policy` | The policy file is there but cannot be used, so the last good setting stays. Written once, until the file reads cleanly again. | Fix the file, or let the user `node` read it. See [how the server reads it](/self-hosting/request-links#how-the-server-reads-the-file). |
| `MAX_CONNECTIONS_PER_IP is not a whole number of at least 1. Using the default, 30.` | A `MAX_*` variable holds something other than a whole number of at least 1. The line names the variable and the default now in use, never the value. Written once at startup for each such variable. | Fix the value, or remove it to keep the default. See [Configuration](/self-hosting/configuration#two-things-about-the-limits). |
| `TRUSTED_PROXY_COUNT is not set, so the default of 1 is in use. Set it to the number of reverse proxies in front of this server, or 0 if there are none.` | The server was started without `TRUSTED_PROXY_COUNT`. Written once at startup. Compose and the Unraid template always pass a value, so it shows only on a server started another way, such as with Node directly, without the variable. | Set the variable. See [Configuration](/self-hosting/configuration#trusted-proxy-count). |
| `TRUSTED_PROXY_COUNT is not a whole number, so the default of 0 is in use. Set it to the number of reverse proxies in front of this server, or 0 if there are none.` | `TRUSTED_PROXY_COUNT` holds a negative number or a value that does not start with a number, such as a word, so the server trusts no proxy. A value that starts with a number is read up to its first other character (`1.5` is `1`) and gets no line. The line names the variable, never the value. Written once at startup. | Set the number of proxies in front of the server, or `0`. See [Configuration](/self-hosting/configuration#trusted-proxy-count). |
| `Refused a request with 403.` | The error handler refused one HTTP request with that status: `403` for a browser origin the server does not allow, or another status under 500. | An occasional one is some page or client sending a bad request, not a fault. If `403` lines show up each time someone uses your own web client, check `CLIENT_URL`. |
| `Refused a connection on /ws from Origin "..." (Host "..."): not CLIENT_URL, a floe.one origin, or this server's own host. Further refusals on /ws are not logged.` | A WebSocket came from an origin the server does not accept. Written once for `/ws` and once for `/socket.io` until the next restart, however many connections are refused. | If the `Origin` is your own server and the `Host` is not, your proxy rewrites `Host`. See [Production deployment](/self-hosting/production#cors-note). |
| `Cloudflare TURN mint failed (...)` | A request to Cloudflare for relay credentials failed. The parentheses hold the reason: `status` and an HTTP status, `no-ice-servers`, an error name such as `TimeoutError`, or the word `error`. At most one line every 5 minutes. | See [TURN relay](/self-hosting/turn-relay#verify). |
| `HTTP server error:` and a stack trace | The server could not bind its port at startup. It exits. | Free the port, or change `PORT`. |
| `Unhandled error (uncaughtException), server still serving:` and a stack trace | An exception nothing anticipated reached the process-level backstop. The word in parentheses can also be `unhandledRejection`. The server kept serving rather than exiting, so the transfers in progress survived. | It is worth reporting. |
| A stack trace on its own | A server-side error (a `5xx`) reached the error handler. | It is worth reporting. |

The `Refused a request with` line carries the status and nothing else, never the origin, the path,
or any of the request's text. Besides `403`, it shows `400` for malformed JSON and `413` for a body
over the size limit. A server image of version 1.11.0 or earlier never writes the `MAX_*` and
`TRUSTED_PROXY_COUNT` lines, and one of version 1.11.3 or earlier never writes the
`TRUSTED_PROXY_COUNT` line about a value that is not a whole number.

To confirm the server is alive, or that a restart actually landed, use the health endpoint below
rather than the logs.

The client container writes Next.js's own lines when it starts. Once it is listening it also warms
its picture cache, and writes one line only if that does not finish:
`Floe: the image warm-up did not finish; pictures are resized on first request instead.` The web
app works either way.

When Docker stops the server, the server closes every connection and exits within 10 seconds, and
logs nothing on the way out. In detail: on `SIGTERM` or `SIGINT` it closes every `/ws` connection
with code `1001` and the reason `Server shutting down`, closes its Socket.IO connections, and stops
accepting new ones. If something is still holding it open 10 seconds later, it exits anyway.

## Health endpoints

The signaling server exposes two status endpoints:

| Endpoint | Purpose | Response |
|----------|---------|---------|
| `GET /health` | Liveness check | `{ "status": "healthy", "uptime": <seconds>, "features": [...] }` |
| `GET /` | Status and timestamp | `{ "status": "ok", "timestamp": "..." }` |

`features` is `["request-1"]` while request links are on and `[]` while they are off. See
[HTTP API](/reference/http-api#get-health).

Point a monitor at `/health`. It is the only one of the two that survives a
[one-domain deployment](/self-hosting/reverse-proxy), where `/` belongs to the
web client and returns a page rather than JSON. `GET /` on the signaling server
is reachable only when you address the server directly, on `:3001` or on its own
subdomain.

Both endpoints pass the same origin check as every other HTTP route. A monitor that sends no
`Origin` header, as `curl` and most uptime services do, is answered. One that runs inside a web
page on another site sends that site's origin, and gets `403` with `{"error":"Bad request"}` while
the server is healthy.

The server image runs the same check on itself every 30 seconds, which is the health state
`docker compose ps` shows. Each check gets 3 seconds to answer, and 3 failed checks in a row mark
the server unhealthy.

The client image checks itself the same way, every 30 seconds, by asking its own `/api/config`, so
`docker compose ps` shows a health state for the client too. A client image of version 1.11.4 or
earlier has no such check and shows none.

## Request links on your server {#request-links}

A self-hosted server offers [request links](/desktop/request-links) only when its policy file turns
them on. The setup, the switch that needs no restart, the limits and the version rule are in
[Turn on request links](/self-hosting/request-links).
