Floe publishes two images to GitHub Container Registry. `docker-compose.yml` pulls both, so self-hosting needs no clone, no Node, and no build.

| Image | Contains |
|-------|----------|
| `ghcr.io/jannskiee/floe-server` | The signaling server. Brokers the WebRTC handshake and issues TURN credentials. Never sees file data. |
| `ghcr.io/jannskiee/floe-client` | The web app, as a self-contained Next.js server. |

Both are public, so `docker pull` needs no login.

## Tags

| Tag | Points at | Use it when |
|-----|-----------|-------------|
| `main` | The latest commit merged to `main` | The default. Every commit is gated behind the full test suite, plus a smoke test of the built image itself. |
| `sha-<short>` | One exact commit, for example `sha-7a1ec76` | You want a build that can never move under you. |
| `1.9.0`, `1.9` | A tagged release | Available once a release exists. |
| `latest` | The newest tagged release | Available once a release exists. |

Pin a tag with `FLOE_IMAGE_TAG`:

```env
FLOE_IMAGE_TAG=sha-7a1ec76
```

<Note>
  The variable is `FLOE_IMAGE_TAG`, not `FLOE_VERSION`. `FLOE_VERSION` belongs to the [CLI installer](/cli/installation) and is written with a leading `v`, as in `v1.9.0`. Image tags carry no `v`, so reusing that name would resolve to a tag that does not exist.
</Note>

## Pinning a digest

A tag can be repointed. A digest cannot, so it is the strongest pin:

```bash
docker buildx imagetools inspect ghcr.io/jannskiee/floe-server:main
```

```yaml
services:
  server:
    image: ghcr.io/jannskiee/floe-server@sha256:6f7818b8...
```

Every tag is verified to resolve to a digest that passed a smoke test before it was applied, so a tag and its digest always refer to an image that was actually started and exercised.

## Architectures

`linux/amd64` only, which covers ordinary VPS and desktop hosts.

There is no `linux/arm64` image yet, so Raspberry Pi and ARM cloud instances need to build from source:

```bash
git clone https://github.com/jannskiee/floe.git
cd floe
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

Building from source needs the repository, since the overlay compiles the working tree.

<Note>
  ARM is not published rather than published-and-broken on purpose. Docker selects the ARM entry automatically on Apple silicon, and the image optimiser fails at load time rather than at build time, so a broken ARM image would look healthy in CI and fail on a user's machine.
</Note>

## Building from source

Contributors, and anyone who wants their own domain in share previews, add the build overlay:

```bash
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

The overlay tags its output `floe-server:dev` and `floe-client:dev`, so a local build never replaces a pulled image under the same name.

## Share previews and canonical links

The published client image omits canonical links, Open Graph images, and sitemap entries. Those have to be written into the HTML when the app is built, so a shared image cannot know which domain it will be served from, and claiming one would mean every self-hosted instance advertising somebody else's site.

To put your own domain in them, build the client yourself:

```bash
NEXT_PUBLIC_SITE_URL=https://files.example.com \
  docker compose -f docker-compose.yml -f docker-compose.build.yml build client
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d
```

This affects only SEO and link previews. Transfers, the signaling connection, and the relay are unaffected, and all of those are configured at runtime.

## Updating

```bash
docker compose pull
docker compose up -d
```
