This page puts the Floe web client and the [signaling server](/glossary#signaling-server) behind
one [reverse proxy](/glossary#reverse-proxy), so the whole instance lives at one address such as
`https://floe.example.com`. It is for anyone taking the Docker stack to production, and it is the
recommended layout: one certificate, one DNS record, and share links that need no extra setting.

## The short version {#the-short-version}

Send `/socket.io/`, `/ws`, `/api/`, and `/health` to the signaling server, except `/api/config`,
and send everything else to the web client. Leave `NEXT_PUBLIC_SOCKET_URL` empty, set `CLIENT_URL`
to your domain, and set `TRUSTED_PROXY_COUNT` to `1`. Then check the result with the commands under
[Verify it works](#verify-it-works).

## Before you start {#before-you-start}

- A domain whose DNS record points at this machine.
- Ports 80 and 443 open to the internet, for visitors and for the HTTPS certificate.
- The [Docker quickstart](/self-hosting/quickstart) stack running on this machine.
- Caddy or nginx installed on the same machine as Docker. The samples below reach the two
  containers at `localhost:3000` and `localhost:3001`.

If your proxy itself runs in a container, such as Nginx Proxy Manager, SWAG, or a Caddy container,
`localhost` inside it is the proxy's own container, and every route answers `502`. Point it at
the host's address instead, or join it to the Compose network and use the service names
`client:3000` and `server:3001`.

## Route table

The client and the signaling server claim different paths, so they coexist on one
origin with no conflicts. Route them like this.

| Path | Goes to | Why |
|------|---------|-----|
| `/socket.io/` | server `:3001` | Browser signaling. [WebSocket](/glossary#websocket) upgrade plus HTTP long-polling fallback. |
| `/ws` | server `:3001` | [CLI](/glossary#cli) and desktop signaling. WebSocket upgrade. |
| `/api/config` | client `:3000` | The client's own runtime config, which tells the browser where the signaling server is. The signaling server has no such route. |
| `/api/` | server `:3001` | The [room](/glossary#room) codes, [TURN](/glossary#turn) credentials, and stats. |
| `/health` | server `:3001` | Health probe. |
| everything else | client `:3000` | The web app, including `/_next/` assets and the request-link page under `/r/`. |

`/api/config` is the one exception to the `/api/` rule, and it needs its own
route in both configs below. Send it to the signaling server and it returns 404.
With the empty socket URL this page recommends below, the browser still lands on
its own origin, which is the right answer, so the mistake never shows. Any
instance that sets a non-empty socket URL loses it silently.
[Verify it works](#verify-it-works) shows how to check it.

<Warning>
  The server answers on `/ws` exactly. A trailing slash or a path prefix does not match, and the
  server answers that upgrade `404 Not Found`, with no log line. If you proxy from a subpath, strip
  the prefix so the server still sees exactly `/ws`. A query string is fine.
</Warning>

A server image of version 1.11.0 or earlier answers such an upgrade with nothing at all, and the
connection closes about 1 second later.

## Proxy configuration

<Tabs>
  <Tab title="Caddy">
    Caddy handles HTTPS certificates and WebSocket upgrades automatically, so the
    whole config is a handful of lines.

    ```nginx Caddyfile
    floe.example.com {
        # Signaling server: WebSockets, room codes, TURN credentials, health.
        handle /socket.io/* {
            reverse_proxy localhost:3001
        }
        handle /ws {
            reverse_proxy localhost:3001
        }
        handle /api/* {
            reverse_proxy localhost:3001
        }
        handle /health {
            reverse_proxy localhost:3001
        }

        # The web client serves its own runtime config here, so it has to win
        # over the /api/* rule above. Caddy orders handle blocks by how specific
        # the path is, so this beats /api/* wherever you put it in the file.
        handle /api/config {
            reverse_proxy localhost:3000
        }

        # Everything else is the web client.
        handle {
            reverse_proxy localhost:3000
        }
    }
    ```
  </Tab>
  <Tab title="nginx">
    nginx needs the `Upgrade` and `Connection` headers set explicitly, or the
    WebSocket handshake fails: the CLI and Floe Desktop cannot connect, and
    browsers are left on HTTP long-polling.

    Save this as a site file, for example `/etc/nginx/conf.d/floe.conf`. nginx reads site files
    inside its `http` block, which is where `map` and `server` have to sit, so do not paste it over
    `nginx.conf` itself. nginx will not load it without a certificate for your domain: get one
    first, for example with Certbot, and put its two paths on the `ssl_certificate` lines.

    ```nginx /etc/nginx/conf.d/floe.conf
    map $http_upgrade $connection_upgrade {
        default upgrade;
        ''      close;
    }

    # Plain HTTP only redirects to HTTPS.
    server {
        listen 80;
        server_name floe.example.com;
        return 301 https://$host$request_uri;
    }

    server {
        listen 443 ssl;
        server_name floe.example.com;

        # Your TLS certificate. nginx refuses a `listen ... ssl` server that has none.
        ssl_certificate     /etc/letsencrypt/live/floe.example.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/floe.example.com/privkey.pem;

        # The client's own runtime config. An exact-match location outranks the
        # regex location below, so this stays on the client.
        location = /api/config {
            proxy_pass http://127.0.0.1:3000;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }

        # Signaling server.
        location ~ ^/(socket\.io/|ws$|api/|health$) {
            proxy_pass http://127.0.0.1:3001;
            proxy_http_version 1.1;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection $connection_upgrade;
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            # The server heartbeats every 30s. Keep idle CLI sockets alive.
            proxy_read_timeout 300s;
        }

        # Web client.
        location / {
            proxy_pass http://127.0.0.1:3000;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
    ```

    Check the file, then load it:

    ```bash Terminal
    sudo nginx -t && sudo systemctl reload nginx
    ```
  </Tab>
</Tabs>

## Floe configuration

Leave the socket URL empty. The browser then talks to whatever host it was
loaded from, which behind this proxy is already the right answer.

```dotenv .env
NEXT_PUBLIC_SOCKET_URL=
CLIENT_URL=https://floe.example.com
TRUSTED_PROXY_COUNT=1
```

```bash Terminal
docker compose up -d
```

Your own domain in share previews and the sitemap needs a client you build yourself, because the
published image cannot carry it: see
[Container images](/self-hosting/images#share-previews-and-canonical-links).

`CLIENT_URL` is matched exactly, including the scheme and with no trailing
slash. `https://floe.example.com` and `https://www.floe.example.com` are
different origins to the CORS check, so use whichever one your users actually
visit.

`TRUSTED_PROXY_COUNT` must equal the number of proxy hops in front of the
signaling server. One reverse proxy means `1`. A CDN in front of that proxy means
`2`. Setting it higher than your real hop count lets clients forge
`X-Forwarded-For` and slip past the per-address [rate limits](/glossary#rate-limit). Leaving it at `0`,
which is what Compose passes when `.env` does not set it, makes every user count
as the proxy's own address. All of them then share one set of limits, and the room seal that
keeps a third network out of a link stops working. With the count at `1`, also keep ports 3000 and
3001 from being reached around the proxy: see
[`TRUSTED_PROXY_COUNT`](/self-hosting/configuration#trusted-proxy-count).

## Using the CLI and the desktop app with a one-domain instance

One address is all the CLI needs. The [share link](/glossary#share-link) it prints resolves to the
same origin, so it opens the web client correctly with no extra flag:

```bash Terminal
floe send --server https://floe.example.com photo.jpg
```

The `--web` flag only exists for split deployments where the client lives at a
different address from the signaling server.

The desktop app takes the same single address. Open Settings and, under
**Advanced**, expand **Server**. Put `https://floe.example.com` in **Server
address** and click **Test**. The test runs three checks in order: that
`/health` answers as a Floe signaling server, that the realtime `/ws` connection
is accepted, and that `GET /api/turn-credentials` returns a usable connection
list. A proxy that forwards only some of those is named in the failure message
instead of breaking silently later.

A server with no TURN [relay](/glossary#relay) still passes, with "Connected, but this server has
no relay: Hide my IP will not work, and some networks will not connect". Floe Desktop 0.3.0 says
"Connected, but there's no relay for Hide my IP" instead. That matters to
[Hide my IP](/glossary#hide-my-ip) address and to any two devices that cannot reach each other
directly. Leave **Share link address** blank on a one-domain instance and the app derives the link
from the server address. See [Desktop app settings](/desktop/settings#server).

The test deliberately does not follow redirects. If you enter an `http://`
address and the proxy redirects it to `https://` on the same host, as the nginx
sample above does with a 301, the test reports "Error: That address redirects to
https://. Start it with https:// and test again". Change the address to
`https://` and click **Test** again. Any other redirect on `/health` is reported
as "Error: That address answered HTTP 301 (likely the web app, not the server)",
with the status the proxy sent, rather than passing.

On this layout the address both apps use is your `CLIENT_URL`, which the server always accepts, so
the `Host` header does not affect them here. It matters on the
[two-hostname layout](/self-hosting/production#cors-note).

Request links are off on a new server until its policy file turns them on. On
this layout they need nothing else from Floe Desktop: the blank **Share link
address** already points at the web client, which serves the page a sender opens.
See [Turn on request links](/self-hosting/request-links).

## TURN does not go through the proxy

If you run the optional coturn relay, its ports stay directly exposed. TURN is not
HTTP, so a reverse proxy cannot carry it. See [TURN relay](/self-hosting/turn-relay)
for the port list and firewall rules.

## Verify it works {#verify-it-works}

```bash Terminal
# Health check through the proxy.
curl https://floe.example.com/health

# TURN credentials endpoint (returns a JSON array of ICE servers).
curl https://floe.example.com/api/turn-credentials

# The client's own config: should answer JSON from the web client.
curl https://floe.example.com/api/config
```

The last one should answer with JSON such as `{"socketUrl":"","commit":null}`. An HTML page that
reads `Cannot GET /api/config` means the request reached the signaling server, so your proxy sends
`/api/config` to the wrong place.

Then open `https://floe.example.com` in a browser. The connection [badge](/glossary#badge) should
read **Ready**. If it reads **Offline**, the `/socket.io/` route is the first thing to check.

The signaling server tells browsers to use HTTPS for its own hostname for one year
(`Strict-Transport-Security`), so a browser that has opened your instance over HTTPS refuses plain
HTTP for that hostname afterward. A server image of version 1.11.0 or earlier extends that to every
subdomain under the hostname as well.

## Prefer two subdomains?

Splitting the client and server across `app.your-domain.com` and
`api.your-domain.com` is still fully supported. See
[Production deployment](/self-hosting/production).

## If something goes wrong

- The page loads but the badge stays **Offline**: see
  [The browser cannot connect to my signaling server](/troubleshooting#the-browser-cannot-connect-to-my-signaling-server).
- **Test** in Floe Desktop stops at the realtime connection: see
  [The Test button says the realtime connection was refused](/troubleshooting#the-test-button-says-the-realtime-connection-was-refused).
- People are turned away with `429` or "Rate limit exceeded" because `TRUSTED_PROXY_COUNT` does not
  match your proxy: see [429, or Rate limit exceeded](/troubleshooting#429-or-rate-limit-exceeded).
