Two commands give you a complete Floe instance on one machine: the web app on port 3000 and the signaling server on port 3001, both from published images. This page is for trying self-hosting locally before you put an instance behind a domain.

## Prerequisites

- [Docker](https://docs.docker.com/get-started/get-docker/) and Docker Compose 2.8.0 or later (`docker compose`, bundled with Docker Desktop and modern Docker Engine; check with `docker compose version`). An older Compose stops with `invalid interpolation format` when it reads `docker-compose.yml`.

## Steps

<Steps>
  <Step title="Download the compose file">
    ```bash Terminal
    curl -fsSLO https://raw.githubusercontent.com/jannskiee/floe/main/docker-compose.yml
    ```
    That is the only file you need. There is nothing to clone and no toolchain to install. In
    Windows PowerShell, type `curl.exe` in place of `curl`: plain `curl` there is another command,
    and it does not take these options.
  </Step>
  <Step title="Start the stack">
    ```bash Terminal
    docker compose up -d
    ```
    Docker pulls the [prebuilt images](/self-hosting/images) and starts the server, then the client once the server reports healthy. Nothing is compiled locally.
  </Step>
  <Step title="Open the app">
    Open [http://localhost:3000](http://localhost:3000) in your browser. The badge at the top right of the card reads **Ready** once the page has reached the signaling server. Pick a file and click **Create secure link**, then paste that link into a second tab to join as the receiver. **Show QR** renders the same link as a scannable code, which is how you receive on a phone once the app is reachable from one (see [Open it from another device](#open-it-from-another-device)).
  </Step>
</Steps>

A `.env` file is optional. Every setting has a working default, so the two commands above are genuinely all you need to try it. To change something, fetch the annotated example alongside the compose file:

```bash Terminal
curl -fsSL https://raw.githubusercontent.com/jannskiee/floe/main/.env.docker.example -o .env
```

In Windows PowerShell this one is `curl.exe` too. Compose reads `.env` when it creates the containers, so run `docker compose up -d` again after each edit. Every variable is described in [Configuration](/self-hosting/configuration).

## What this runs

This starts the stack in **STUN-only** mode: with no relay configured, the server hands every client two public Google STUN servers and nothing else. Floe uses direct peer-to-peer connections, which work on most home and mobile networks. No files pass through the server.

To support peers behind strict firewalls, symmetric NAT, or CGNAT, add a [TURN relay](/self-hosting/turn-relay).

[Request links](/desktop/request-links) are off in this stack until a policy file turns them on. See [Turn on request links](/self-hosting/request-links).

The CLI and Floe Desktop work with this instance too. They connect to the signaling server, so give them `http://localhost:3001`, not the web app's port. See [Use a self-hosted server](/cli/self-hosted-server).

## Open it from another device

The defaults assume the browser and the server are on the same machine. To reach the app from another device on your network, set **both** of these in `.env` to your machine's LAN IP:

```dotenv .env
NEXT_PUBLIC_SOCKET_URL=http://192.168.1.x:3001
CLIENT_URL=http://192.168.1.x:3000
```

```bash Terminal
docker compose up -d
```

Then open the app at `http://192.168.1.x:3000` on the sending machine too, not `localhost:3000`. The share link and its QR code carry whichever address the page was loaded from, so a sender sitting on `localhost` hands the phone an address that only resolves back to the phone.

No rebuild: the client reads its server address at runtime. `CLIENT_URL` matters as much as the socket URL, because it is the origin the server's CORS check and its WebSocket origin check allow, and without it the browser is blocked even though the page loads.

The CLI and Floe Desktop on another device take the server's address on port 3001. For the links they hand out to open the web app, also give them its address on port 3000, as `--web` or **Share link address**: only `localhost` pairs the two ports for them automatically.

## Change the ports

Set `PORT` and `CLIENT_PORT` in `.env` to publish the signaling server and the web app on host ports other than 3001 and 3000. On one machine that is all it takes: while `NEXT_PUBLIC_SOCKET_URL` and `CLIENT_URL` are unset, each follows its port. If you have set either one yourself, it has to carry the new port:

- A `NEXT_PUBLIC_SOCKET_URL` you set has to name the server's address on the new port, or the browser keeps looking for the old one.
- A `CLIENT_URL` you set has to name the web app's address on the new port, or the server refuses the page's connections.

For example, to move both:

```dotenv .env
PORT=4001
CLIENT_PORT=8080
```

```bash Terminal
docker compose up -d
```

No rebuild is needed for either one.

<Warning>
  A `CLIENT_URL` set in `.env` does not follow `CLIENT_PORT`. Change the port with an old `CLIENT_URL` still in place and the page loads but never connects: the badge stays on **Offline**. Remove the line, or give it the new port. The same holds for `NEXT_PUBLIC_SOCKET_URL` and `PORT`. A `docker-compose.yml` downloaded before October 2026 has fixed defaults, so with it both addresses always have to be set.
</Warning>

## If something goes wrong

- The page loads and the badge stays on **Offline**: see [The browser cannot connect to my signaling server](/troubleshooting#the-browser-cannot-connect-to-my-signaling-server).
- The server answers `403` after you changed an address or a port: see [Browser requests are blocked, and the server answers HTTP 403](/troubleshooting#browser-requests-are-blocked-and-the-server-answers-http-403).
- Two devices on different networks never connect: see [The transfer never starts](/troubleshooting#the-transfer-never-starts).
