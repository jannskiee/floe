You can run the whole Floe stack yourself, independently of `floe.one`: the web app, the [signaling server](/glossary#signaling-server), and an optional TURN [relay](/glossary#relay). The standard setup is [Docker Compose](/glossary#docker-compose), which pulls two published images and starts the stack with one command. Unraid templates and a plain Node.js run are covered too.

## What you are hosting

The signaling server introduces two devices to each other and then steps aside. **File data never passes through it.** Technically, it passes the [WebRTC](/glossary#webrtc) connection details between the two [peers](/glossary#peer) (offer, answer, and [ICE](/glossary#ice) candidates), and once a relay is set up it also issues relay credentials that last 24 hours. Transfers go [peer-to-peer](/glossary#peer-to-peer) over encrypted WebRTC data channels. A relay is optional, and it carries the (still encrypted) traffic only when a firewall or [NAT](/glossary#nat) rules out a [direct connection](/glossary#direct-connection), or when a transfer is set to use the relay.

## Components

| Component | Description |
|-----------|-------------|
| `client` | Next.js web app, on container port 3000 |
| `server` | Node.js signaling server, on container port 3001 |
| `coturn` | Optional [self-hosted](/glossary#self-hosted) [TURN](/glossary#turn) relay (profile-gated in Docker Compose). Alternatively, use managed Cloudflare Realtime TURN with no extra container. |

Those are the ports inside the containers. In production you normally put both
behind a single domain, so your users never see either one. See
[Run behind one domain](/self-hosting/reverse-proxy).

Both images run the newest release by default, not what floe.one runs: floe.one serves the web
app from the newest code, which is what the web-app pages of these docs describe. Until the next
release, your instance can word some things differently, and
[What an older web app shows](/self-hosting/operations#older-web-app-versions) lists each place.

## What the web app on your domain serves

The client image serves the same site as floe.one, under your address:

- The transfer page, and the page a [request link](/glossary#request-link) opens, under `/r/`.
- floe.one's other pages, unchanged: `/download`, `/how-it-works`, `/privacy`, and `/terms`. The
  privacy policy and the terms describe floe.one and the servers its maintainers run, not your
  instance, and no setting replaces them.
- The [CLI](/glossary#cli) install scripts, at `/install.sh` and `/install.ps1`.
- `/docs`, which sends visitors on to the same page of floe.one's documentation instead of serving
  the documentation itself.

The web app refuses to be shown inside another page: every page carries a `frame-ancestors 'none'`
policy and `X-Frame-Options: DENY`. A dashboard that embeds apps in a frame shows a blank frame
for Floe, so open it in its own tab. The headers are fixed when the image is built, and no setting
changes them.

## Who can connect

One instance serves every Floe client. They share one wire protocol, so any two of
them can transfer with each other on your server.

| Client | How it points at your instance |
|--------|-------------------------------|
| Web app | Loads from your `client` container. Nothing for your users to configure. |
| CLI | `floe send --server https://floe.example.com`. See [Use a self-hosted server](/cli/self-hosted-server). |
| Floe Desktop | In Settings, under **Advanced**, expand **Server** and fill in **Server address**. **Test** checks the address before you rely on it, and **Use default server** returns the app to `api.floe.one`. See [Desktop app settings](/desktop/settings#server). |

Both peers must be on the same server. Servers do not talk to each other.

The CLI and Floe Desktop need no setting on the server: `CLIENT_URL` governs browsers only. A
[reverse proxy](/glossary#reverse-proxy) in front of the server has to pass the `Host` header through for them, as
[Origins the server accepts](/self-hosting/production#cors-note) explains.

## Off until you turn it on

Two features need setup before a new instance has them.

A new instance has no TURN relay. Two devices that cannot reach each other directly do not
connect. A transfer that insists on the relay stops with a message before it starts: [Hide my IP
address](/glossary#hide-my-ip) in Floe Desktop, Hide my IP on a request link's page, or
`--relay-only` on the CLI. See
[TURN relay](/self-hosting/turn-relay).

[Request links](/desktop/request-links) are off. Until a policy file turns them on,
**Make link** in Floe Desktop answers "Request links are off on this server". See
[Turn on request links](/self-hosting/request-links).

## Run one instance, not several

The signaling server keeps [rooms](/glossary#room), [room codes](/glossary#room-code), open
request links, and its rate limiters in the memory of a single process.

<Warning>
  Putting two replicas behind a load balancer does not scale Floe out. It breaks pairing,
  because the two peers can land on different replicas and never find each other.
</Warning>

One instance goes a long way. File data never passes through it, so it is brokering a handshake
and then getting out of the way. If you need redundancy, use a failover pair rather than a
load-balanced set, and accept that the switch loses every room and room code the old instance
held, as a [restart](/self-hosting/operations#common-commands) does.
