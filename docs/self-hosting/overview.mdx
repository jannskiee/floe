You can run the whole Floe stack yourself, independently of `floe.one`: the web app, the signaling server, and an optional TURN relay. The standard setup is Docker Compose, which pulls two published images and starts the stack with one command. Unraid templates and a plain Node.js run are covered too.

## What you are hosting

The signaling server brokers WebRTC connection setup (offer, answer, ICE candidates) and issues TURN credentials that last 24 hours. **File data never passes through it.** Transfers go peer-to-peer over encrypted WebRTC data channels. TURN is optional and relays (still encrypted) traffic only when a direct connection is not possible or a transfer is set to use the relay.

## Components

| Component | Description |
|-----------|-------------|
| `client` | Next.js web app, on container port 3000 |
| `server` | Node.js signaling server, on container port 3001 |
| `coturn` | Optional self-hosted TURN relay (profile-gated in Docker Compose). Alternatively, use managed Cloudflare Realtime TURN with no extra container. |

Those are the ports inside the containers. In production you normally put both
behind a single domain, so your users never see either one. See
[Run behind one domain](/self-hosting/reverse-proxy).

## Who can connect

One instance serves every Floe client. They share one wire protocol, so any two of
them can transfer with each other on your server.

| Client | How it points at your instance |
|--------|-------------------------------|
| Web app | Loads from your `client` container. Nothing for your users to configure. |
| CLI | `floe send --server https://floe.example.com`. See [Use a self-hosted server](/cli/self-hosted-server). |
| Floe Desktop | In Settings, under **Advanced**, expand **Server** and fill in **Server address**. **Test** checks the address before you rely on it, and **Use default server** returns the app to `api.floe.one`. See [Desktop app settings](/desktop/settings#server). |

Both peers must be on the same server. Servers do not talk to each other.

`CLIENT_URL` governs browser traffic only. CLI and desktop peers connect over `/ws` and
send your server's own address as their origin, which the server accepts when it is your
`CLIENT_URL` or names the same host as the `Host` header your proxy forwards. They reach
your server without `CLIENT_URL` listing them, as long as the proxy does not rewrite `Host`.

## Off until you turn it on

Two features need setup before a new instance has them.

A new instance has no TURN relay. Two devices that cannot reach each other directly do not
connect, and a transfer that insists on the relay (**Hide my IP address** in Floe Desktop,
`--relay-only` on the CLI) stops with a message before it starts. See
[TURN relay](/self-hosting/turn-relay).

[Request links](/desktop/request-links) are off. Until a policy file turns them on,
**Make link** in Floe Desktop answers "Request links are off on this server". See
[Turn on request links](/self-hosting/request-links).

## Run one instance, not several

The signaling server keeps rooms, room codes, open request links, and its rate limiters in
the memory of a single process.

<Warning>
  Putting two replicas behind a load balancer does not scale Floe out. It breaks pairing,
  because the two peers can land on different replicas and never find each other.
</Warning>

One instance goes a long way. File data never passes through it, so it is brokering a handshake
and then getting out of the way. If you need redundancy, use a failover pair rather than a
load-balanced set, and accept that the switch loses every room and room code the old instance
held, as a [restart](/self-hosting/operations#common-commands) does.
