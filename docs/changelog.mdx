Floe ships on two version lines. `vX.Y.Z` releases the `floe` CLI and the container images for the server and web app you can run yourself. `desktop-vX.Y.Z` releases Floe Desktop for Windows. The web app at floe.one is on neither line: it runs the newest code as soon as it is merged, so a web app change can be live there before the `vX.Y.Z` entry that lists it. The two lines never need to match, and no release so far has changed the transfer protocol, so every version of Floe sends to and receives from every other one. Request links need a current Floe Desktop and a server that offers them.

Each entry lists the parts it changed. Filter on the right to see only the ones you use.

<Update label="Unreleased" tags={["Desktop"]}>

  - In History, a receive by code now lists its empty files by name, where one empty file received alone used to read "0 files". Contributed by [@Detoy](https://github.com/Detoy).
  - In Settings, **Hide my IP address** and **Contribute to global stats** now switch back when Floe cannot save the change, as the other switches already do. They used to keep showing the new setting while a request link went on with the saved one.

<Update label="v1.11.7" description="2026-10-28" tags={["Web", "Self-hosting"]}>
  **A file added twice on the main page is now listed and sent once, its FAQ questions are headings, and a self-hosted server given a port Node refuses now stops with an error**

  - On the main page, a file you add again, by picking it again or by dropping it after picking it, is no longer listed a second time, so it is sent once and counted once in the count and total above the list. The page tells files apart by name, size and modified time: two files with the same name are both kept when either of the others differs, and two different files that match in all three are listed once. Such a file used to be listed and sent twice, and Floe Desktop and `floe` saved the second copy under a numbered name such as `report (1).pdf`. Contributed by [@dharamdan01](https://github.com/dharamdan01).
  - On the main page, FAQ questions are headings for screen-reader navigation, and each question button is linked to its answer. Contributed by [@Martin-e60](https://github.com/Martin-e60).
  - Self-hosting: a signaling server given a [`PORT`](/self-hosting/configuration#port) that Node refuses, such as `70000` or `3001.5`, now writes `HTTP server error:` and exits with code 1, as it does when its port is taken, so a supervisor such as systemd with `Restart=on-failure` sees the failure. It used to log `Unhandled error (uncaughtException), server still serving:` while nothing was listening, then exit with code 0, which reads as a clean stop. Contributed by [@OKAN-SOFTWARE](https://github.com/OKAN-SOFTWARE).
  - Self-hosting: the published images are rebuilt as `1.11.7`, with the web app and server changes above. If you pinned `FLOE_IMAGE_TAG=1.11.6`, move to `1.11.7`.
  - CLI: `floe` has no visible changes in this release. Its version moves with the images, and it transfers with every other Floe version as before.
</Update>

With such an address the relay list never loaded, so peers that need a relay could not connect, and the global counter and the receiver's byte report failed with nothing in the page or the logs to say why. Contributed by [@Detoy](https://github.com/Detoy).

  - Web app: the main page keeps the screen awake only while a transfer wants it. Coming back to the tab used to take the screen wake lock again whenever the connection was up, so an idle or finished page kept the screen on. A send started while the tab was hidden still gets its lock when the tab comes back. Contributed by [@LetMeSleep8h](https://github.com/LetMeSleep8h).
  - Web app: on the main page, once a link is created, a screen reader now names the QR button by the words on it, "Show QR" or "Hide QR", and says whether the QR code is open, where it used to call it "Toggle QR code", words that appear nowhere on screen. Contributed by [@vaishaldsouza](https://github.com/vaishaldsouza).
  - Web app: on the main page, a screen reader now says which of the header's About, CLI, Desktop and FAQ buttons is the section you are reading, where only the filled highlight showed it. Contributed by [@vaishaldsouza](https://github.com/vaishaldsouza).
  - Web app: when a link opens the "Link Invalid" card, a screen reader now reads the card's heading and its sentence, "This link is incomplete, already in use, or locked to the networks that first used it.", as soon as the card appears, where the card used to replace the receive steps without a word. Contributed by [@ayushdwivedi-stack](https://github.com/ayushdwivedi-stack).
  - CLI: [tab completion](/cli/flags#shell-completion) now offers interface names for `--iface`, offers only folders for `-o` in Bash and Zsh, and stops offering files where a code, a link or a server address goes. Contributed by [@SauravMukherjee44](https://github.com/SauravMukherjee44).
  - The published images are rebuilt as `1.11.6`, with the web app changes above. The server's code is the same as in 1.11.5. If you pinned `FLOE_IMAGE_TAG=1.11.5`, move to `1.11.6`.
</Update>

  - When the main page shows its red banner, a screen reader now reads the sentence as soon as it appears and names the banner's X "Dismiss", where it used to say nothing until the banner was found and called the X only "button". Contributed by [@BillWGong](https://github.com/BillWGong).

  - Self-hosting: the published images are rebuilt as `1.11.5`, with the changes above. The client image moves Next.js to 16.4.2 and React to 19.3.1. If you pinned `FLOE_IMAGE_TAG=1.11.4`, move to `1.11.5`.

<Update label="desktop-v1.0.1" description="2026-10-19" tags={["Desktop"]}>
  **A very large receive no longer fills the storage History is kept in, and closing Floe while a setting is saved no longer freezes the window**

  - The window no longer goes blank when the storage it keeps History in is full. A receive by code now keeps the first 200 file names in its History row, as a request link drop already does, so a very large folder no longer fills that storage, and an expanded History row lists at most its first 200 names, older rows included. <Update label="v1.11.4" description="2026-10-19" tags={["Web", "CLI", "Self-hosting"]}>
  **The web app shows a green check mark when every file's SHA-256 matched, and `floe` and the signaling server hold firmer limits**

  - When every file's SHA-256 matched, the check marks in front of "3 files received" on the receiving page and beside "All Files Sent!" on the Send page are green, as in Floe Desktop. The line "SHA-256 matched" that sat under them is gone; a screen reader still reads it. When a file could be checked by its size only, the check mark is gray, where it was green every time.
  - On the Send page "All Files Sent!" turns green with its check mark when the receiving app reports that every file matched, usually a moment after the last byte leaves. Until then, and for good with a receiver that sends no such report, both stay gray.
  - A request link's page still says "Their app reports every file's SHA-256 matched.", and `floe send` and `floe receive` still print `Verified   SHA-256 matched`.
  - In a browser without WebRTC, such as Tor Browser or Firefox with WebRTC turned off, a receiving page now says so in its red banner and does not join the room, so the link still works when opened in another browser. A sending page says so as soon as it loads. The sentence stays up through a reconnect.
  - A send whose connection closed just as its last file finished now says "Connection lost. The other device may have closed the tab." instead of "All Files Sent!", because the end of that file never reached the receiver.
  - CLI: `floe` reads at most 64 KiB of the server's answer for connection details or a short code, so a server that answers with far more can no longer make it use gigabytes of memory. A longer answer counts as unreadable: the transfer goes on with STUN only and the usual warning, `floe send` shares the link without a code, and `floe receive` says it could not resolve the code.
  - CLI: on Windows, a `floe update` whose download failed partway no longer leaves the partial download in your temp folder.
  - Self-hosting: a `TRUSTED_PROXY_COUNT` that is a word or a negative number still counts as 0, and the server now says so in one line at startup.
  - Self-hosting: a `CLIENT_URL` written with a trailing slash, such as `https://app.example.com/`, no longer shuts your own web app out.
  - Self-hosting: the example coturn configuration refuses to relay to private, loopback, link-local and other reserved addresses. A `turnserver.conf` you already made does not change: copy the new lines in from the example. If a device that uses the relay can be on the relay's own private network, such as a relay at home that you also use from home, also uncomment the example's `allowed-peer-ip` line for that network, as the TURN relay page explains.
  - Self-hosting: the signaling server sends the stats counter's bytes to Upstash Redis one call at a time, adding the bytes reported in the meantime to the next call, so a stalled Upstash no longer holds an open call for every report.
  - Self-hosting: the signaling server now disconnects a browser connection that has stopped reading once about 1 MB is waiting for it, as it already did for the CLI and Floe Desktop, so a flood aimed at such a connection no longer piles up in the server's memory until the connection times out. A page cut off this way stays disconnected until it is reloaded.
  - Self-hosting: when you build the web app yourself, as an image or with `pnpm build`, the Sentry build plugin no longer sends Sentry a report about the build: a session, and sometimes a timing sample, never any visitor data. `NEXT_TELEMETRY_DISABLED` did not turn it off.
  - Self-hosting: the published images are rebuilt as `1.11.4`, with the web app and server changes above. The client image moves `@sentry/nextjs` to 11.8.0, so if you send its reports to a Sentry project of your own, some span fields arrive under their 11.x names. If you pinned `FLOE_IMAGE_TAG=1.11.3`, move to `1.11.4`.
</Update>

<Update label="desktop-v1.0.0" description="2026-10-17" tags={["Desktop"]}>
  **Floe Desktop 1.0.0: Floe Desktop and request links are out of Beta**

  - Floe Desktop and request links are no longer labeled Beta: **Request link** under **Receive** has no **Beta** tag. How request links work is unchanged, and Floe's server can still turn them off for everyone.

<Update label="desktop-v0.3.2" description="2026-10-16" tags={["Desktop"]}>
  **A request-link drop Floe was closed during now shows what it saved, and quitting during a receive no longer leaves an unfinished file behind**

  - Quitting Floe Desktop while a piece of a received file was being written could make it wait five seconds before it closed, and leave the unfinished `.part` file in the folder. It now closes without the wait and removes the `.part` file.
  - A request-link drop that Floe was closed during, by you or by Windows, now shows on the next launch as stopped, for example "Floe was closed · 4 of 12 files saved", with **Show in folder**, and adds its row to History. The files it saved had no History row.
  - On Windows 10, a file whose name begins with a reserved device name and a dot, such as `aux.h` or `con.txt`, is saved with an underscore in front (`_aux.h`), in a receive and in a request-link drop, and so is a request link label such as `con.notes`, which names the folder each drop is saved in. Windows 10 opens such a name as the device, so the receive stopped at that file, and with such a label every drop stopped before a file was saved. Windows 11 keeps the names as sent.
  - A send now reports at once a receiver that stops it while the send is waiting for that receiver to take in more data. The reason showed only once the receiver took in more data, which could take a minute or more. If it took in nothing, the send ended after a minute with "The connection dropped before the transfer finished" in its place.
  - A send their Floe stops because a file name or folder path is too long to save now reads "A file name or folder path is too long for their computer. Shorten it or zip it first". It named only a folder path.
  - A request-link drop stopped by a path too long for Windows now reads "A file name or folder path was too long for Windows", because one long file name stops it too. It named only a folder path.
  - **Make link** now checks that Floe can write in the **Save to** folder, and says "Couldn't use that folder" when it cannot, as it does for a missing drive. A folder such as Program Files made a link that failed at the first drop.
  - Against a Floe server from before request links, **Make link** now says "This Floe server doesn't offer request links". It said "Request links are off on this server", which no setting on that server could change.
  - "Missed a request at" and "Link ended at" now give the date when it was not today, for example "Link ended at Oct 15, 3:42 PM". A link can last 7 days, and a time alone read as today.
  - **Cancel drop** now reads **Stopping** and takes no second click until the drop has stopped, which can take a few seconds. Nothing on screen said the click was taken.
  - A request-link drop with no label that saved no file is titled "Nothing saved" in History. It was titled "0 files".
  - On a request link made with Auto-accept, a drop that asks because Floe could not tell whether the connection is relayed now says "Asks because Floe couldn't check the connection". It asked with no reason.
  - A request link made with Auto-accept on a drive that cannot carry Windows' downloaded-file mark, such as a FAT32 or exFAT USB drive, now reads "Ends today, 2:05 PM · Asks first, Windows can't mark files on E:" while it waits. It said "Accepts automatically", though every drop asked.
  - A request-link file whose name already ended in `.floe-blocked` when it was sent no longer counts as a file Floe renamed. The finished drop said it had renamed it, and **Show in folder** asked first because of it.
  - The folder name on a finished request-link drop keeps its date, time and any number such as `(2)` whole, and a label in Chinese, Japanese, Korean or emoji is shortened to fit. A wide label pushed the time out of view.
  - After **Decline**, keyboard focus goes to "Request declined", with **Keep waiting** one Tab away. A held Enter no longer presses **Make another link** or **Keep waiting**. Focus no longer moves to **Make another link** when a link ends long after a **Retry now** that did not reconnect, and no longer takes back a click made right after **Close link** or **Cancel drop**.
  - **Send with Floe** in File Explorer now shows for any number of selected files. Windows hid it when more than 15 were selected. An entry an earlier Floe Desktop added is brought up to date the next time that copy starts.
  - **Open** on a received file whose name holds `#` or `%` now opens that file. It could open the wrong thing or nothing.
  - The Settings gear in the title bar now waits while **Close Floe?**, **Start over?** or **Reset all settings?** is open, as Ctrl+, already did. It opened or closed Settings under the question.
  - On a PC without the Microsoft WebView2 runtime, a failed download of its installer now shows an error instead of closing Floe Desktop at once. The app is now built on Wails 2.16 and Go 1.27.
</Update>

<Update label="v1.11.2" description="2026-10-16" tags={["CLI", "Web", "Self-hosting"]}>
  **On Windows, stopping a receive partway through a file no longer leaves the unfinished file behind, and `floe` names the server's connection limit instead of a lost server**

  - On Windows, a Ctrl+C in `floe receive` that landed while a piece of a file was being written could make `floe` wait its full five seconds before it exited, and leave the unfinished `.part` file in the folder. It now exits without the wait and removes the `.part` file.
  - `floe send` and `floe receive` now end with `Error: the server is limiting connections from this network. Wait a minute and try again.` when the server turns the connection away by its limits on connections from one network. They said `connection closed before the server assigned a role`, or `failed to join room: websocket: close sent`, as if the server had gone. `floe send --to` prints the same sentence.
  - A file name or folder path too long for the receiving computer, one long file name with no folder included, now ends `floe send` with `Error: A file name or folder path is too long for their computer. Shorten it or zip it first.` (`floe send --to` prints it without `Error: `, then how many files were saved, such as `Nothing was sent.`), and a pick `floe send --to` cannot describe ends with `A file name or folder path is too long to send. Shorten it or zip it first.` Both named only a folder path and said to zip deeply nested folders.
  - `floe send` now reports at once a receiver that stops the transfer while `floe send` is waiting for it to take in more data. A receiver that stops without closing the connection, as a browser does, was reported only once it took in more data, which could take a minute or more. If it took in nothing, the send ended after a minute with `backpressure stall: peer not draining` in its place.
  - On Windows 10, `floe receive` saves a file whose name begins with a reserved device name and a dot, such as `aux.h` or `con.txt`, with an underscore in front (`_aux.h`). Windows 10 opens such a name as the device, so the receive stopped at that file. Windows 11 and other systems keep the name as sent.
  - Release builds of `floe` for macOS now need macOS 13 Ventura or later. They are built with Go 1.27, which no longer supports macOS 12. On macOS 12, stay on 1.11.1 or follow [Build from source](/cli/installation#build-from-source) with Go 1.26.
  - Web app: a browser that receives now tells the sender once it holds every file, as `floe receive` and Floe Desktop do. `floe send` 1.11.0 or later and Floe Desktop 0.3.0 or later wait for that word. A file the page could not keep after the last byte, such as one the browser ran out of memory for, now ends the send as a failure with the reason instead of `Sent`. A tab closed before the word arrives ends it as unconfirmed. When every file matched, `floe send` shows `Verified   SHA-256 matched`, Floe Desktop its green check mark, and a browser that sends to another browser "SHA-256 matched".

<Update label="v1.3.0" description="2026-06-17" tags={["CLI", "Web", "Self-hosting"]}>
  **One-command install and self-update**

  - `floe update` now works on all platforms (script installs, manual installs). It downloads, verifies, and replaces the running binary in one step.
  - Re-running the install script (`curl -fsSL https://floe.one/install.sh | sh` or `irm https://floe.one/install.ps1 | iex`) also upgrades an existing install in place.
  - If floe was installed via Homebrew, Scoop, or Winget, `floe update` detects this and prints the correct package manager command instead.
  - Fixed a browser receiver bug where a `Buffer` view was retained across chunk boundaries instead of being copied, which could corrupt received data.
  - Security: updated `ws`, `esbuild`, and `postcss` transitive dependencies to address published advisories.
</Update>

<Update label="v1.1.0" description="2026-06-16" tags={["CLI", "Web"]}>
  **Transfer reliability and browser fixes**

  - Fixed several CLI transfer sync bugs that could cause stalled or incomplete transfers, especially in CLI-to-CLI sessions. Added cross-implementation loopback tests to prevent regressions.
  - Fixed an issue where the in-app browser detection could steal the receiver slot from a legitimate peer, preventing the transfer from starting.
  - Fixed duplicate WebRTC signal handling that could break transfers after a reconnect.
  - Redesigned the in-app browser warning page for clarity.
  - Upgraded the CLI to Pion WebRTC v4 (includes Pion DTLS v3).
  - Performance: improved browser-to-browser transfer throughput with better backpressure tuning.
</Update>

<Update label="v1.0.0" description="2026-06-14" tags={["Web", "CLI", "Self-hosting"]}>
  **Initial public release**

  - Browser-based peer-to-peer file transfer at [floe.one](https://floe.one). No account, no installation, no file storage.
  - `floe` CLI for macOS, Linux, and Windows. Fully interoperable with the browser client.
  - End-to-end DTLS encryption on all transfers, direct and relayed.
  - Optional TURN relay fallback for peers behind strict firewalls or carrier-grade NAT (capped at 2 GB per session).
  - Self-hosting support via Docker Compose. See [Self-Hosting](/self-hosting/overview).
  - Mintlify documentation site at [docs.floe.one](https://docs.floe.one).
</Update>
