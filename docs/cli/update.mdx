```bash floe update
floe update [--check]
```

Replaces the running `floe` binary with the latest release, or with `--check` only reports
whether a newer one exists.

<Info>
  `floe update` never touches Floe Desktop, which updates on its own track. Desktop builds ship on
  their own `desktop-v*` tags as GitHub pre-releases, so neither `floe update` nor the install
  scripts ever pick them up. See the Update section of
  [Install the desktop app](/desktop/installation#update).
</Info>

## Script and manual installs

Run the built-in update command:

```bash Terminal
floe update
```

This asks GitHub for the latest release, downloads the correct archive for your OS and
architecture, verifies its SHA-256 against the release's `checksums.txt`, and replaces the running
binary in place:

```text Output
Current version: 1.10.11
Checking for updates... v1.11.0
Update available: 1.10.11 -> v1.11.0
Downloading v1.11.0...
Updated to v1.11.0
```

When nothing newer exists, it prints `Already up to date (1.11.0)` after the first two lines and
stops. `floe update` installs nothing when the checksum does not match. Unlike the install
scripts, it also installs nothing when the release lists no checksum for the archive.

On macOS and Linux, if floe lives in a root-owned directory such as `/usr/local/bin` (the
install script's default), the final swap needs elevation, so floe asks for your sudo password
once. Everything before that step (download, checksum, extraction) runs as your normal user. If
sudo is not installed, the update stops and tells you to re-run as root or reinstall with the
install script. On Windows no elevation is involved: floe renames the running executable aside
and moves the new one into place.

To check for an update without installing:

```bash Terminal
floe update --check
```

It prints the same first lines and, when a newer release exists, ends with
``Run `floe update` to install.`` instead of downloading anything.

You can also re-run the original install script at any time to upgrade:

```bash Terminal
# macOS / Linux
curl -fsSL https://floe.one/install.sh | sh

# Windows
irm https://floe.one/install.ps1 | iex
```

## Package manager installs

If you installed floe via a package manager, use the standard upgrade command for that tool.

`floe update` detects a package-managed install from the binary's path and stops before it
contacts GitHub, rather than replacing the binary behind your package manager's back. It names
the right command and exits with status 1, for example:

```text Output
Error: installed via homebrew - run `brew upgrade floe` to update
```

The same guard applies to `floe update --check`.

| Install method | Upgrade command |
| -------------- | --------------- |
| Homebrew (macOS) | `brew upgrade floe`, or `brew upgrade --cask floe` to name the cask explicitly |
| Winget (Windows) | `winget upgrade jannskiee.floe` |
| Scoop (Windows) | `scoop update floe` |

Detection is a substring match for `homebrew`, `cellar`, `linuxbrew`, `scoop`, or `winget`
anywhere in the binary's path, in any capitalization, so a script install that happens to live
under a directory containing one of those words is treated as package-managed too.

A binary built from source is checked before any of this and stops with
`Cannot update a dev build.` whatever its path, so this section applies only to release builds.

## The update hint

When a newer release exists, `floe version` prints an extra line:

```text Output
Update available: v1.x.x  run `floe update` to upgrade
```

Only `floe version` runs this check on its own, never `send` or `receive`, and it keeps the
answer for 24 hours. `floe update` and `floe update --check` are a separate, deliberate check:
they ask GitHub directly and ignore that cache. Set `FLOE_NO_UPDATE_CHECK=1` to suppress the hint
entirely; it does not change what `floe update` does. See
[The update check](/cli/version#the-update-check) for where the cache lives and how to clear it.

## Version compatibility

You do not need to match versions with the person on the other end. Floe peers on different
releases interoperate, so a version difference by itself is never a problem. If a release ever
changes the transfer protocol in a breaking way, Floe detects it before any data moves and tells
whichever side is older to update. See
[Protocol versioning](/reference/transfer-protocol#protocol-versioning) for the details.

Request links are the one exception. They are a newer feature, not a protocol change:
`floe send --to` needs `floe` 1.11.0 or later (an older `floe` stops with
`Error: unknown flag: --to`), and the link itself comes from Floe Desktop 0.3.0 or later on a
server that offers request links.
