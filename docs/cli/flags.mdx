Every flag and environment variable that `floe` reads, its exit codes and timeouts, and what a
script needs to know.

## Global flags

Every command accepts these, but only `send` and `receive` act on them. `floe version` and `floe update` parse them and then ignore them, so `floe version --server https://floe.example.com` is accepted and changes nothing. The one exception is the pair `--relay-only` and `--no-relay`, which every command refuses together.

| Flag | Default | Description |
|------|---------|-------------|
| `--server <url>` | `https://api.floe.one` | Signaling server URL. Use `http://localhost:3001` for local testing or your self-hosted server URL. |
| `--no-relay` | `false` | Drop every TURN entry from **your** ICE list, so you offer nothing relayed. It is one-sided: the peer can still offer a relay, and if that path wins the CLI proceeds over it, so pass the flag on **both** ends when it has to be a guarantee. When no path forms at all the failure is a generic connection error after about 30 seconds, never a message about the relay. |
| `--relay-only` | `false` | Route everything through the TURN relay and never try a direct path, so the other side sees the relay's address instead of yours. It is the command-line twin of the desktop app's **Hide my IP address** switch, and it applies to your side only. While it is on, the 2 GB relay cap applies to every transfer, even on a network that could have connected directly; see [File size limits](/how-it-works/2gb-limit). It needs a relay to exist: against a server that offers STUN only, the command stops before the transfer starts and names the flag, rather than timing out about 30 seconds later. Cannot be combined with `--no-relay`. Also settable with `FLOE_RELAY_ONLY=1`. |
| `--web <url>` | _(auto-detected)_ | Web app URL included in the browser link printed by a plain `floe send`, the only command that reads it. Auto-detected from `--server`: `https://api.floe.one` maps to `https://floe.one`, `http://localhost:3001` maps to `http://localhost:3000`, and any other server maps to itself, on the assumption that one origin serves both the API and the web app. Set `--web` only when your web app has its own hostname. |
| `--iface <name>` | _(all interfaces)_ | Restrict WebRTC to network interfaces whose name contains this value (case-insensitive). Repeat the flag or separate names with commas, so `--iface Ethernet --iface Wi-Fi` and `--iface Ethernet,Wi-Fi` do the same thing. Use it when a VPN or virtual-machine adapter (Tailscale, VMware, WSL, Hyper-V) slows connection setup; see [slow to connect](/troubleshooting#slow-to-connect-when-a-vpn-or-virtual-machine-is-running). |

The desktop app has equivalents for three of these. `--server` and `--web` are **Server address** and **Share link address**, under Advanced in **Settings**, and `--relay-only` is the **Hide my IP address** toggle under Privacy. `--no-relay` and `--iface` have no desktop equivalent: Floe Desktop can require the relay but never refuse it. See [Desktop app settings](/desktop/settings).

## `floe send` flags {#floe-send-flags}

Specific to the `send` command.

| Flag | Default | Description |
|------|---------|-------------|
| `--to <link>` | _(none)_ | Send through a [request link](/desktop/request-links) made in Floe Desktop instead of creating a room code. Put the whole link in quotes, including everything after the `#`. No link is printed, so `--web` has no effect with it, and the link has to belong to the server in effect. See [Send through a request link](/cli/send#send-through-a-request-link). |

## `floe receive` flags {#floe-receive-flags}

Specific to the `receive` command.

| Flag | Default | Description |
|------|---------|-------------|
| `--output <dir>`<br />`-o` | `.` | Directory to save received files. Created if it does not exist, before Floe connects. |
| `--yes`<br />`-y` | `false` | Accept incoming files without the confirmation prompt. |
| `--no-report` | `false` | Do not report the transferred byte count to Floe's public global counter. See [Opting out of the global counter](#opting-out-of-the-global-counter) below. |

## `floe update` flags {#floe-update-flags}

Specific to the `update` command.

| Flag | Default | Description |
|------|---------|-------------|
| `--check` | `false` | Report whether a newer release exists and exit without installing it. On an up-to-date binary the flag changes nothing: `floe update` prints `Already up to date (1.11.0)` and stops either way (the installed version carries no leading `v`). On a package-managed install the update guard runs first, so `--check` stops with the upgrade command for your package manager instead of a version report. See [Update the CLI](/cli/update). |

## Help and version flags

These come from the CLI framework rather than from Floe itself.

| Flag | Default | Description |
|------|---------|-------------|
| `--help`<br />`-h` | `false` | Print usage and exit. Works on every command, so `floe send --help` and `floe receive --help` each print that command's own flags. |
| `--version`<br />`-v` | `false` | Print the installed version and exit, for example `floe 1.11.0`. Root only: `floe --version` works, `floe send --version` does not. See [Alternatives](/cli/version#alternatives). |

`floe completion` and `floe help` come from the same place and are not part of Floe's own interface. Run `floe completion --help` if you want shell completion.

## Environment variables

`floe` has five environment variables of its own. If you run your own signaling server, set it once in your environment instead of passing `--server` on every command.

| Variable | Equivalent flag | Description |
|----------|-----------------|-------------|
| `FLOE_SERVER` | `--server` | Signaling server URL for `send` and `receive`. Any non-empty value counts. While it names your own server, a link made on floe.one is refused before any network call, by `floe receive` and by `floe send --to`: pass `--server https://api.floe.one` for that command. See [Use a self-hosted server](/cli/self-hosted-server#links-carry-no-server). |
| `FLOE_WEB` | `--web` | Web app URL used for the browser link printed by `floe send`. Any non-empty value counts. |
| `FLOE_RELAY_ONLY` | `--relay-only` | Set to `1` to route every transfer through the relay, hiding your IP address from the other side. A typed `--no-relay` overrides it for that one command, since the two can never both be on. |
| `FLOE_NO_STATS` | `--no-report` | Set to `1` to never report byte counts. Applies to `floe receive`. See [Opting out of the global counter](#opting-out-of-the-global-counter). |
| `FLOE_NO_UPDATE_CHECK` | _(no flag)_ | Set to `1` to suppress the "Update available" hint that `floe version` prints. It does not affect transfers or `floe update` itself. |

The last three act only on the exact value `1`: `true`, `yes` or any other value does nothing.

A flag always beats its variable, so you can override the setting for a single command without unsetting anything:

```bash macOS and Linux
export FLOE_SERVER=https://floe.example.com
floe send photo.jpg                                # uses floe.example.com
floe send photo.jpg --server https://api.floe.one  # the flag wins, just this once
```

On Windows PowerShell:

```powershell Windows
$env:FLOE_SERVER = "https://floe.example.com"
floe send photo.jpg
```

Trailing slashes are trimmed, so `https://floe.example.com/` and `https://floe.example.com` behave the same.

Set `FLOE_WEB` only when your web app runs on a different host from your signaling server. Leave it unset and share links point at the same host as your server, which is what you want when one domain serves both. The only exceptions are Floe's own deployment and the local dev pair, which are special-cased to their web hosts as described under `--web` above.

Pion, the WebRTC library inside `floe`, reads log settings of its own from `PION_LOG_` variables. Left alone, `floe` turns some of Pion's log lines off. For every command, those are the relay client's, which can quote an unauthenticated reply, and the packet mux's, which is internal noise. During `floe send --to`, they are also the peer connection's and the data channel's, which can quote text the other side chose. Setting a variable that turns a Pion log level on, such as `PION_LOG_TRACE=ice`, leaves all of them on, so set one only while debugging.

## In scripts and CI {#in-scripts}

`floe` reads no configuration file and asks one question, so a job needs only flags, environment variables and exit codes.

- **Accept without a prompt.** `floe receive` asks `Accept? [Y/n]` before it saves anything. Pass `-y` to skip the question.
- **A closed stdin accepts too.** The prompt declines only on `n` or `no`. A closed or piped stdin gives it an empty answer, which accepts, so `echo | floe receive <code>` receives without `-y`. Leaving `-y` out therefore does not stop a job from receiving. Pass it anyway, so the intent is on the command line rather than in the shell's plumbing.
- **Exit codes.** `0` is success, `1` is any error, and `130` is an interrupt (`Ctrl+C` or `SIGTERM`). There are no others. See [Exit codes](#exit-codes).
- **What success means for a send.** `floe send --to` exits `0` only after the other side's Floe confirmed that every file arrived. A plain `floe send` to `floe receive` 1.11.0 or later, or to Floe Desktop 0.3.0 or later, exits `0` only after the receiver said it saved every file. To a browser, or to an older receiver, it exits `0` once the other side's connection has acknowledged all the data. See [File checks](/how-it-works/file-checks#delivery-confirmation).
- **A send waits as long as it takes.** `floe send` has no time limit of its own while it waits for the other side to connect, so give the job a timeout if it must not hang.
- **Pass the link when the wait may be long.** A room code stops working after 10 minutes at most, and the link works for as long as that `floe send` runs: see [How long a code and a link last](/how-it-works/signaling#code-and-link-lifetime). `floe receive` takes either.
- **Environment variables.** Set the server once with `FLOE_SERVER`. Set `FLOE_NO_STATS=1` on a job that receives, so test transfers do not add to the public counter, and `FLOE_NO_UPDATE_CHECK=1` if the job runs `floe version`. See [Environment variables](#environment-variables).
- **Streams.** Status lines, the boxes, the prompt, progress and `Warning:` lines go to stdout. Errors, every refusal line and the `Canceled.` line go to stderr.

## Opting out of the global counter

After a successful transfer, the **receiver** sends only the total byte count to the signaling server it is connected to (`api.floe.one` by default, or your own server when you set `--server` or `FLOE_SERVER`) to power the public "transferred globally" counter. No file names, contents, or identity are included. The **sender** never reports.

Errors are ignored, so a failed report never changes the outcome of a transfer. The request goes out after every file is written and the summary has printed, and it carries a 5-second timeout, so an unreachable server can delay `floe receive` from exiting by a few seconds but never affects the files.

To opt out for a single transfer, pass `--no-report`:

```bash Terminal
floe receive olive-tiger-castle --no-report
```

To opt out permanently, set `FLOE_NO_STATS=1` in your environment (for example in your shell profile):

```bash Terminal
export FLOE_NO_STATS=1
floe receive olive-tiger-castle
```

When opted out, no request is sent to the server and the global counter is not incremented for that transfer. The transfer itself is unaffected.

The browser and Floe Desktop have a switch of their own for the same report. See [Aggregate statistics](/security-privacy#aggregate-statistics).

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Success. For `floe send --to`, only after the other side's Floe confirmed that every file arrived. Also what `floe update` returns on a build compiled from source, which prints `Cannot update a dev build.` and stops. |
| `1` | Any error: a usage mistake, a transfer that failed, a code that would not resolve, a declined transfer, a refused link, or a package-managed install refusing to self-update. Every outcome of `floe send --to` other than success and `Ctrl+C`. |
| `130` | Interrupted, by `Ctrl+C` or by `SIGTERM`. Floe prints `Canceled.` to stderr and removes the `.part` file it was writing, waiting at most 5 seconds for that before it exits. `floe send --to` prints its own line instead, `Canceled. Nothing was sent.` or `You stopped this drop.` with how many files were saved. |

`floe` with no arguments prints help and exits `0`.

## Timeouts

Floe gives up rather than hanging, and the limits differ by phase. The ones you are most likely to
meet:

| Phase | Limit |
|-------|-------|
| Sender waiting for the other side to join | No limit |
| Establishing the connection | 30 seconds, then [`timed out establishing a connection`](/troubleshooting#timed-out-establishing-a-connection). A peer that leaves during setup ends it at once, with [`the other side left before the connection was established`](/troubleshooting#the-other-side-left-before-the-connection-was-established) |
| Receiver connected, sender never starts | 30 seconds, then [`connected, but no data arrived from the sender within 30s`](/troubleshooting#connected-but-no-data-arrived-from-the-sender-within-30s) |
| Sender waiting for the receiver to accept | 120 seconds, sized for a human answering the `Accept? [Y/n]` prompt, then [`timed out waiting for ack`](/troubleshooting#timed-out-waiting-for-ack). With `--to`, 9 minutes 45 seconds, the request link's answer window, then `They did not answer in time. Nothing was sent.` |
| A transfer that stops making progress | 60 seconds |
| Sender waiting, after the last byte, for `floe receive` 1.11.0 or later or Floe Desktop 0.3.0 or later to say it saved everything | No limit while the connection lasts; about 30 seconds after the receiver goes silent, [`the connection closed before the receiver confirmed delivery`](/troubleshooting#the-connection-closed-before-the-receiver-confirmed-delivery) |
| The byte-count report after a transfer | 5 seconds, and it never affects the files |

A `floe receive` can sit for up to about 10 seconds after printing its summary. That is a 5-second
grace period so the final acknowledgment reaches the sender, plus the report. When that
acknowledgment is slow to reach the sender, it waits up to 35 seconds from sending it before the
report. The full list is in the [transfer protocol reference](/reference/transfer-protocol#timeouts),
and every Floe limit is collected in [Limits](/reference/limits).

## Examples

Use a local dev server for both sender and receiver:

```bash Terminal
floe send photo.jpg --server http://localhost:3001
floe receive olive-tiger-castle --server http://localhost:3001
```

Disable relay fallback (direct connections only):

```bash Terminal
floe send photo.jpg --no-relay
```

Hide your IP address from the other side by forcing the relay (the 2 GB cap applies):

```bash Terminal
floe send photo.jpg --relay-only
```

Point the browser link at a custom web client:

```bash Terminal
floe send photo.jpg --server https://api.example.com --web https://app.example.com
```

Save received files to a specific folder and auto-accept:

```bash Terminal
floe receive olive-tiger-castle -o ~/Downloads -y
```

See [Use a self-hosted server](/cli/self-hosted-server) for more server configuration examples.
