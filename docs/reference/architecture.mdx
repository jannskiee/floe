This page maps Floe's moving parts for contributors and for self-hosters who want to know what they
are running. It covers the components, both signaling transports and every message on them, request
rooms, the server's limits, room codes, and the byte counter. For the plain-language version, see
[How a transfer works](/how-it-works/signaling).

## The short version {#the-short-version}

Two devices meet in a [room](/glossary#room) on the [signaling server](/glossary#signaling-server),
swap the details they need to connect, and then send the files straight to each other over an
encrypted [data channel](/glossary#data-channel). The server never sees a file. Browsers talk to it
over Socket.IO, and the CLI and Floe Desktop over a plain [WebSocket](/glossary#websocket), and both
kinds meet in the same rooms.

## Components

| Component | Runtime and port | What it does |
|-----------|------------------|--------------|
| Client | Next.js 16 (React 19), port 3000 | The browser UI and its [WebRTC](/glossary#webrtc) [peer](/glossary#peer), via simple-peer |
| Server | Node.js (Express 5, Socket.IO 4, ws 8), port 3001 | Brokers signaling, registers room codes, issues [relay](/glossary#relay) credentials, keeps the byte counter |
| CLI | Go 1.26 (Pion WebRTC v4) | Headless sender and receiver |
| Desktop | Wails v2 (Go backend, React frontend) | Windowed sender and receiver. Windows amd64 today |
| TURN relay | Cloudflare Realtime TURN on floe.one, or your own coturn on ports 3478 and 5349 | Forwards encrypted packets when no direct path exists |

The [CLI](/glossary#cli) and Floe Desktop share one Go transfer engine in `cli/engine/`, joined by
the `go.work` workspace file, so they behave identically on the wire.

**File data never passes through the signaling server**, and only end-to-end-encrypted packets
ever transit the [TURN](/glossary#turn) relay. Every byte of every file travels over a WebRTC data
channel between the two peers.

## A session, end to end

1. The sender generates a UUID room id.
2. The sender joins the room, which is the first time the server sees the room id. The server
   assigns the role `sender`.
3. The CLI and Floe Desktop then register the room id with `POST /api/code` to get a
   [room code](/glossary#room-code). The web app never does.
4. The sender displays what it has to share and waits: a link on every surface, a room code on the
   CLI and Floe Desktop, and a QR code on the web app and Floe Desktop. All three surfaces put the
   room id in the **fragment** of the link. Browsers never send a fragment to a server, so opening
   the link keeps the room id out of request URLs, `Referer` headers, and analytics.
5. The receiver joins the same room, after resolving the room code with `GET /api/code/:code` if
   that is what it was given. The server assigns `receiver`, retires the room's code, and tells the
   sender someone arrived.
6. The sender creates a WebRTC offer and sends it through the server.
7. The receiver answers.
8. Both exchange [ICE](/glossary#ice) candidates as they are gathered, rather than in one batch.
9. The data channel opens and the signaling server plays no further part.

Each side fetches the ICE server list from `GET /api/turn-credentials` before it builds its peer
connection.

A [request link](/glossary#request-link) turns the first half around. Floe Desktop joins first with
its host token and receives. The sender, on the page the link opens or in `floe send --to`, comes
second through `request-join`, and sends. Floe Desktop still creates the offer, once the server
tells it the sender arrived. See [Request rooms](#request-rooms).

## The server runs as one process

Rooms, room codes, request-link reservations, and every rate limiter live in that process's memory.
Nothing is persisted except the global byte counter, and only when a Redis database is configured,
so a restart forgets every room, code, reservation, and limiter window.

<Warning>
  Running two replicas behind a load balancer does not scale Floe out. It breaks pairing, because
  the two peers can land on different replicas and never see each other. Run one instance.
</Warning>

A single small server goes a long way, since no file data passes through it.

## Two signaling transports, one room registry

| Transport | Path | Used by |
|-----------|------|---------|
| Socket.IO | `/socket.io/` | The web app, including the page a request link opens |
| WebSocket | `/ws` | The CLI and Floe Desktop |

Both share the same in-memory `rooms` registry, `Map<roomId, [peer, peer]>`, which is what makes
browser-to-CLI and browser-to-desktop transfers work with no translation layer.

The WebSocket path must be exactly `/ws`. A query string is fine. A WebSocket upgrade on any other
path, a trailing slash or a prefix included, is answered `404 Not Found`, which matters when you
put Floe behind a proxy. An upgrade whose request target cannot be read as a path is answered
`400 Bad Request`. Both answers are plain text and write no log line. A server image of version
1.11.0 or earlier sends no answer to an upgrade on another path, and closes the socket about a
second later.

A room id is matched exactly as sent. The server accepts a UUID in either letter case, but it
stores an ordinary room under the id as it arrived. Two peers that send the same UUID in different
case therefore land in two different rooms. Send one consistent spelling. A request room is the
exception: its id is read in lowercase on every message.

### Socket.IO events

Client to server:

| Event | Payload | Description |
|-------|---------|-------------|
| `join-room` | `roomId: string` | Join an ordinary room, or make it. Must be a UUID. |
| `request-join` | `roomId: string` | Ask for the sending seat of a request room. The page a request link opens sends it. See [Request rooms](#request-rooms). |
| `signal` | `{ signal, target?, roomId? }` | Forward an SDP message or ICE candidate to the other peer. `target`, when set, must be that peer's id. `roomId` is sent but ignored; routing uses the room the server already has this peer in. |
| `ping` | callback | A round-trip latency probe, not a keepalive. The web app's transfer page sends one every 2 seconds, and the sender's view shows the result as the ping readout beside the connection dot. |

Server to client:

| Event | Payload | Description |
|-------|---------|-------------|
| `room-joined` | `{ role: "sender" \| "receiver" }` | Confirms a `join-room` and assigns a role by join order: the first peer in is `sender`, the second is `receiver`. |
| `request-joined` | `{ role: "visitor" }` | Confirms a `request-join`: this socket holds the sending seat of a request room. |
| `user-connected` | `peerId: string` | The receiver arrived. Sent to the sender. |
| `signal` | `{ signal, sender: peerId }` | A signal from the other peer. |
| `peer-disconnected` | `{}` | The other peer's connection closed. |
| `room-full` | `{}` | The room is full, sealed, or reserved. Every case is listed under [When the server answers room-full](#when-the-server-answers-room-full). |
| `host-absent`, `link-ended`, `disabled` | `{}` | A `request-join` did not get the seat, or a seated sender lost it before the room sealed. A sender in a sealed room also gets `disabled` when its host reopens the room while request links are off. See [Request rooms](#request-rooms). |
| `error` | `{ message: string }` | The frame was refused. On this transport the only message is `Invalid room ID`, for a room id that is not a UUID string. |

### WebSocket messages

Every message is a JSON object with a `type` field. A frame that is not a JSON object, or whose
`type` the server does not know, is ignored with no reply.

Client to server:

| `type` | Other fields | Description |
|--------|-------------|-------------|
| `join-room` | `roomId: string` | Join an ordinary room, or make it. |
| `join-room` | `roomId: string`, `hostToken: string`, `endsIn?: number` | The host join that makes or reclaims a request room. Any `join-room` carrying `hostToken` takes this path. See [Request rooms](#request-rooms). |
| `request-join` | `roomId: string` | Ask for the sending seat of a request room. `floe send --to` sends it. |
| `request-seal`, `request-reopen`, `request-close` | `roomId: string` | The host's control messages for its request room. The server acts on one only when it comes from that room's seated host, and never answers it, except that a `request-reopen` sent while request links are off ends the room: the host gets `refused` with `disabled`. |
| `signal` | `signal`, `target?: string`, `roomId?: string` | Forward a signal. `target`, when set, must be the other peer's id. The Go client sends `roomId`, and the server ignores it as it does on Socket.IO. |
| `ping` | - | Answered with `{"type":"pong"}`. Only Floe Desktop sends it, on the connection that holds a request link (see [Keeping connections alive](#keeping-connections-alive)). |

Server to client:

| `type` | Other fields | Description |
|--------|-------------|-------------|
| `room-joined` | `role: "sender" \| "receiver" \| "host"` | Role assignment. `host` answers a host join; the other two come from join order. |
| `request-joined` | `role: "visitor"` | Confirms a `request-join`: this socket holds the sending seat of a request room. |
| `user-connected` | `id: string` | The second peer arrived: the receiver of an ordinary room, or the sender on a request link. Sent to the first peer. |
| `signal` | `signal`, `sender: string` | A signal from the other peer. |
| `peer-disconnected` | - | The other peer's connection closed. |
| `room-full` | - | The room is full, sealed, or reserved, or a host join was turned away. Every case is listed under [When the server answers room-full](#when-the-server-answers-room-full). |
| `host-absent`, `link-ended`, `disabled` | - | The same cases as on Socket.IO. |
| `refused` | `code: "disabled" \| "limited" \| "busy"` | A host join was turned down, or request links were turned off under a waiting host. Only a host receives it. See [Request rooms](#request-rooms). |
| `pong` | - | Answer to a client `ping`. |
| `error` | `message: string` | The frame was refused: `Invalid room ID`, or `Invalid host token` on a host join. |

### When the server answers room-full {#when-the-server-answers-room-full}

The same frame answers several situations on both transports:

- A `join-room` into an ordinary room that already holds two peers.
- A `join-room` from a third network into a sealed ordinary room (see [A room seals](#a-room-seals)).
- A plain `join-room` aimed at a request room's id.
- A `request-join` whose seat is taken, whose link is sealed or used, or whose link has spent its
  seating budget.
- A seated sender that the host unseats with `request-reopen`.
- Everyone in an ordinary room that sits on a request link's id, when the link's host takes the id
  back with its token.
- On `/ws` only, a host join for a link that was already used, or whose token does not match the
  reservation.

### What the server relays, and what it drops {#what-the-server-relays}

Both transports cap a single inbound message at 1 MB (1,000,000 bytes); an oversized WebSocket
frame closes the connection. Signaling messages are SDP and ICE candidates, so this is a guard
rather than a limit anyone meets. The server relays a `signal` only when all of these hold:

| Bound | Value |
|---|---|
| Shape | Plain JSON: objects, arrays, strings, finite numbers, booleans, and `null` |
| Depth | At most 8 levels of nesting |
| Length | At most 65,536 characters by the server's own count |

The count is of the JSON text as the server would write it, keys included. Every double quote,
backslash, control character, and half of a surrogate pair counts as 6. A line ending of CR and LF
is two control characters, so it costs 12, and an SDP of many lines reaches the bound well before
its JSON text is 65,536 characters long. A real offer carrying every candidate of a many-adapter PC
comes to under a quarter of the bound.

Anything else is dropped with no answer. So are a `signal` whose value is empty or false, a signal
with nobody to receive it, and one whose `target` is not the other peer. On Socket.IO, the event
must carry an object with a `signal` in it.

### A room outlives a one-sided drop

When a peer disconnects, the server removes only that peer, sends `peer-disconnected` to the one
left, and keeps the room for it. That is what lets a browser rejoin the same room after its socket
reconnects. The room is deleted when the last peer leaves.

A peer that leaves an ordinary room by joining another room on the same connection leaves without
that notice: the peer left behind hears nothing until it acts.

### A room seals {#a-room-seals}

Once peers from two different client addresses have each sent a `signal` that the server routed to
the other peer, a peer from a third address gets `room-full` until the room is deleted. Joining
alone does not count an address, so a sender that reconnects from a new address beside its own
stale connection does not seal its own room.

The address is the one the per-IP limits count (an IPv6 address counts by its /64), so peers that
share one address are never sealed out. It is read through `TRUSTED_PROXY_COUNT`, so a server
behind a proxy needs that set right for the seal to work (see
[Configuration](/self-hosting/configuration#trusted-proxy-count)). The server keeps a keyed hash of
each counted address for as long as the room exists, never the address itself. A request room does
not use this seal; it has its own, described under [Request rooms](#request-rooms). What the seal
means for the people in a transfer is in
[How a transfer works](/how-it-works/signaling#a-room-holds-exactly-two-people).

### Keeping connections alive {#keeping-connections-alive}

The connection is kept alive below this layer. Every 30 seconds the server sends a WebSocket
protocol-level ping to each `/ws` client and terminates any that did not answer the previous one
with a matching pong. The Go client answers automatically, so nothing in Floe's own message set is
involved. Socket.IO connections use that library's default heartbeat, a ping every 25 seconds. A
[reverse proxy](/glossary#reverse-proxy) therefore needs an idle read timeout longer than 30
seconds, or it cuts healthy connections.

Floe Desktop also runs a check of its own on the connection that holds a request link. It sends
the `ping` message every 25 seconds, and treats 60 seconds without any message from the server,
this `pong` included, as a lost connection. `floe send`, `floe receive`, and Floe Desktop's ordinary
transfers never send it.

A `/ws` client that stops reading is cut off as well: once more than 1 MB of output is waiting for
it, the server terminates the connection instead of sending more.

### How a /ws connection is closed {#how-a-ws-connection-is-closed}

| Close code | When |
|---|---|
| `1008` | The connection was over the per-IP connection limit, or its address already held as many open connections as `MAX_SOCKETS_PER_IP` allows. It completes its handshake and is then closed, with the reason `Rate limit exceeded`. |
| `1009` | The client sent a frame larger than 1 MB. |
| `1001` | The server is shutting down, with the reason `Server shutting down`. |

### What a Go peer accepts {#what-a-go-peer-accepts}

The CLI and Floe Desktop bound what the server and the other peer can make them hold during setup.
A client built to talk to them has to stay inside these:

| Bound | Value | Past it |
|---|---|---|
| One frame from the signaling server | 2 MiB | The connection to the server ends. |
| Remote ICE candidates over one connection | 256 | Further candidates are dropped, with no error. |
| Candidates held before the remote description arrives | 64 | Further candidates are dropped, with no error. |
| One candidate | 1 KiB | That candidate is dropped, with no error. |

A client that puts many candidates in its SDP, or trickles more than 256, still connects to
browsers and can fail against the CLI and Floe Desktop with no message.

## Request rooms {#request-rooms}

A request link gets a room that is reserved for the Floe Desktop that made it, rather than seated
by join order: that app holds the room and receives, and the person sending joins second. Request
rooms exist only while the server's policy file turns request links on (see
[Turn on request links](/self-hosting/request-links)), and `GET /health` lists `request-1` in
`features` while it does.

| Sent by | Message | What it does |
|---------|---------|--------------|
| Floe Desktop, on `/ws` | `join-room` with `roomId`, `hostToken` and `endsIn` | Makes the room, or reclaims it. |
| The sender, on Socket.IO (the page a request link opens) or on `/ws` (`floe send --to`) | `request-join` with the room id | Takes the sending seat, and never makes a room. |
| Floe Desktop | `request-seal` | Seals the room once the data channel is open. It does nothing while no sender is seated. |
| Floe Desktop | `request-reopen` | Unseals the room and unseats a seated sender with `room-full`, so the next `request-join` can take the seat. Sent when a pairing ends without a drop, and when you click **Keep waiting** after a decline. |
| Floe Desktop | `request-close` | Ends the room and its reservation. A sender seated in a room that has not sealed gets `link-ended`. |

### The host token and the room id {#the-host-token-and-the-room-id}

The host token is 32 random bytes, sent as 43 base64url characters. Floe Desktop keeps it in
memory, and it leaves the app only inside the host's `join-room`. The room id in the link is
derived from it:

1. Take the [SHA-256](/glossary#sha-256) of the text `floe-request-room-v1:` followed by the token.
2. Keep the first 16 bytes.
3. Set the version and variant bits as for a version 4 UUID.
4. Write the result as lowercase hex in the `8-4-4-4-12` form.

Someone who holds the link knows the room id, and cannot work back to a token that derives it, so
nobody but the app that made the link can take its first seat. The server keeps only the SHA-256
of the token itself, never the token, and compares digests in constant time. The CLI's engine and
the server are both pinned to one file of test vectors,
`cli/engine/signaling/testdata/derivation-vectors.json`.

### The host join {#the-host-join}

`endsIn` is the link's remaining life in milliseconds. The server keeps it as an end time on its
own clock, and ignores a missing or out-of-range value. It reads `endsIn` only when the join makes
the room: a reclaim keeps the end the room already has, so a later join cannot move it.

The server checks a host join in this order, and the first answer that applies is the one sent:

| Check | Answer |
|---|---|
| The room id is not a UUID | `error` with `Invalid room ID` |
| The token is not 43 base64url characters, or the room id is not its derivation | `error` with `Invalid host token`, even while request links are off |
| Request links are off | `refused` with `disabled` |
| The link was already used | `room-full` |
| The token does not match the reservation | `room-full` |
| The reservation's host is connected, or has been away for 10 minutes or less | `room-joined` with role `host`: a reclaim, which is not a new link. The newest connection holding the token takes the seat |
| The network has made 20 links in the last 24 hours | `refused` with `limited` |
| The network already holds 10 open links, or the server holds 5,000 | `refused` with `busy` |
| None of the above | `room-joined` with role `host`: the room is made |

A reservation whose host has been away longer than its grace is let go at this point, and the join
goes on as a new link. An ordinary room that sits on the id is taken back before the limits are
checked: everyone in it gets `room-full` and loses their seat. A host join that is over more than
one request-link limit answers `limited`, because the daily budget is checked first.

### The sender's request-join {#the-senders-request-join}

The server checks a `request-join` in this order:

1. The connection has already sent 30 `request-join` frames in its current 60-second window: no
   answer at all. The window opens at the first frame after the last one ran out, so it is not a
   rolling minute.
2. The room id is not a UUID: `error`.
3. Request links are off: `disabled`.
4. No reservation has that id: `link-ended` if a link with that id ended within the last 24
   hours, otherwise `host-absent`. An id that is no request link at all answers the same way, so
   the answer confirms nothing.
5. This connection already holds that room's seat: no answer at all.
6. The link is sealed or used: `room-full`.
7. The host is away in its grace: `link-ended` once the link has passed the end its host named,
   otherwise `host-absent`.
8. The seat is taken: `room-full`.
9. The link has seated a sender 6 times in the last minute: `room-full`, and nothing changes.
10. Otherwise: `request-joined` with role `visitor` to the sender, and `user-connected` to the host.

The two cases with no answer are why a client should not send `request-join` again to be safe. The
request-link page and `floe send --to` each wait 10 seconds for an answer, then report that none
came.

### How a request room seals and ends

A request room seals as soon as both seats have routed a connection-setup message, or when the host
sends `request-seal`, and from then on `request-join` answers `room-full`. `POST /api/code` refuses
a request room's id, and making the room retires any code already registered for that id, so no
code ever points at one.

The reservation outlives an empty room. When the host's socket closes, the server keeps the
reservation for about 10 minutes so Floe Desktop can reclaim its seat with the same token, which
does not count as a new link. The edge is exact for the host: a host join up to 10 minutes after
the socket closed is a reclaim, and a later one makes the link again, which counts toward the daily
budget. The once-a-minute sweep then removes the reservation, so it lasts between 10 and 11
minutes. When the host leaves, a sender seated in a room that has not sealed gets `host-absent` and
loses the seat. A sender in a sealed room keeps the seat and gets `peer-disconnected`.

Whatever its host is doing, a reservation ends at the first sweep after it turns 7 days and 10
minutes old. Nobody is sent a frame for that, a connected host included.

What `request-join` answers afterward depends on how the link ended:

| How the link ended | What the server keeps | What `request-join` answers |
|--------------------|-----------------------|-----------------------------|
| A `request-close` for a sealed room, which means the link was used | A mark that the link was used, for 24 hours | `room-full`. A host join with the link's token answers `room-full` too, so the link cannot be made again |
| A `request-close` for a room that still waited. Floe Desktop sends it for **Close link**, at the link's end time, and when it quits | A mark that the link ended, for 24 hours. It holds no room and no seat, and making the link again with its token clears it | `link-ended` |
| A lapse with no `request-close`, because the computer slept, went offline or was turned off | The room id and the end its host named in `endsIn`, until 24 hours after that end | `host-absent` until that end, since Floe Desktop may come back, then `link-ended` for 24 hours |

A link past the 7-day ceiling is marked ended at once. A lapsed link younger than that, whose host
named no end, leaves no mark and keeps answering `host-absent`.

All of it is in memory: a restart forgets every reservation and every mark. An open Floe Desktop
makes its waiting link again when it reconnects, which counts toward its network's daily budget.

Turning request links off in the policy file ends every request room that is not sealed, at the
server's next once-a-minute read of the file. A seated host gets `refused` with `disabled`, and a
seated sender gets `disabled`. A sealed room is left alone, because its drop runs on the data
channel and needs nothing more from the server. If its host sends `request-reopen` while request
links are still off, as Floe Desktop does for **Keep waiting** after a decline, the server ends
that room the same way. A server image of version 1.11.0 or earlier reopens it instead, and no
`request-join` can reach it.

Floe Desktop takes `refused` with `disabled` as its link's end. Once links are back on, a link
whose host was told answers `link-ended` for 24 hours, and a link whose host was away answers from
the end it named, as a lapsed one does.

## Rate limiting

Every limit below lives in the server's memory. The ones with an environment variable have their
home in [Configuration](/self-hosting/configuration), and this table repeats their defaults. The
request-link limits are fixed in the server; what they mean for the people on a server is in
[Turn on request links](/self-hosting/request-links#request-link-limits). For the limits of the web
app, the CLI, and Floe Desktop as well, see [Limits](/reference/limits).

| Limit | Value | Applies to |
|-------|-------|-----------|
| Connections | 30 per IP per 60 seconds (`MAX_CONNECTIONS_PER_IP`) | Socket.IO and `/ws`, shared |
| Open connections | 60 per IP at a time (`MAX_SOCKETS_PER_IP`) | Socket.IO and `/ws`, shared |
| TURN credentials | 20 per IP per 60 seconds (`MAX_TURN_REQUESTS_PER_IP`) | `GET /api/turn-credentials` |
| Room codes | 60 per IP per 60 seconds (`MAX_CODE_REQUESTS_PER_IP`) | `POST /api/code` and `GET /api/code/:code`, shared |
| Failed code lookups | 10 per IP per 60 seconds (`MAX_FAILED_CODE_RESOLVES`) | `GET /api/code/:code`, misses only |
| Stats reports | 60 per IP per 60 seconds, **not configurable** | `POST /api/stats/report` |
| Active codes | 10,000 held in memory (`MAX_ACTIVE_CODES`) | `POST /api/code`, returns `503` when full |
| New request links | 20 per IP per rolling 24 hours, **not configurable** | A host `join-room` that makes a request room. A reclaim is free; making a link again after its reservation ended counts. Answers `refused` with code `limited` |
| Open request links | 10 per IP at a time, **not configurable** | Request rooms made from one address that have not ended or been used. A new one past the cap answers `refused` with code `busy` |
| Request rooms | 5,000 held in memory, **not configurable** | Open request links from every address together; a new one past the cap answers `refused` with code `busy` |
| Used request links | 10,000 marks held in memory, **not configurable** | Links someone connected through. They hold no place under the room cap |
| Ended request links | 20,000 marks held in memory, **not configurable** | Links that ended before anyone used them: closed, lapsed past the end their host named, or ended by the policy file |
| Request joins | 30 per connection per 60 seconds, **not configurable** | `request-join`; a frame past the budget is dropped with no answer |
| Seatings | 6 per request room in any 60 seconds, **not configurable** | A `request-join` that would take the seat answers `room-full` instead |

Past either mark cap the oldest mark goes. A link whose used mark went answers `host-absent` again
and can be made again; a link whose ended mark went answers `host-absent` again.

The per-IP counters live in plain `Map`s and are swept every 60 seconds. The three HTTP limiters
and the failed-lookup budget answer `429`. The connection limiter is not an HTTP response. A
Socket.IO handshake over the limit is rejected in middleware, which the browser sees as a
`connect_error`, and the web app's transfer page then retries with a growing delay. A `/ws`
connection over the limit is closed with code `1008` (see
[How a /ws connection is closed](#how-a-ws-connection-is-closed)).

The open-connection cap is checked first, in the same two places, and refuses with the same
`Rate limit exceeded`, so a client cannot tell the two apart and does not need to. It counts a
connection once the server has admitted it and gives the place back when that connection closes,
however it closes: the client leaves, or a heartbeat in
[Keeping connections alive](#keeping-connections-alive) ends a connection that stopped answering,
such as one whose network dropped. It needs no sweep, because a count is dropped when it reaches
zero. An Engine.IO session that never joins a namespace is not counted, as it is not rate limited
either, and Socket.IO closes it after 45 seconds. A session whose client leaves the namespace
without closing is closed by the server at once.

Every per-IP limiter records only what it admits. A refused connection attempt leaves no
timestamp, just as the three HTTP limiters return the `429` before recording anything. A client
that keeps retrying therefore gets back in as soon as its admitted connections age out of the
60-second window. Setting a `MAX_*` variable to `0` does not disable a limit, and
neither does any other value that is not a whole number of at least 1. The server keeps the
default and logs one line, as
[Configuration](/self-hosting/configuration#two-things-about-the-limits) describes.

The failed-lookup budget counts the other way around, on purpose: only a miss is recorded, and a
lookup that finds a live code costs nothing. The budget is spent before the lookup runs. A caller
that has run out therefore gets the same `429` whether the code it asked about is live, expired, or
was never registered. That includes a code that works: once an address has 10 misses inside the
window, every lookup from it answers `429` until misses age out.

The budget exists because the shared code limiter is a volume control rather than a guessing
control: 60 requests a minute is 60 guesses a minute, indefinitely. A budget of 10 failures a
minute is far more than a real receiver needs, since a receiver whose code works never spends any
of it.

The active-code cap is global rather than per-IP, because it guards the size of the in-memory
registry. It counts stored entries rather than genuinely live ones, so the number can briefly
include codes that have already expired but that the once-a-minute sweeper has not cleared.

Every per-IP limiter normalizes the client address before it counts. A port that a proxy appended
to the address is dropped first. An IPv6 address keys on its `/64` prefix, so everyone sharing a
`/64` shares one bucket. That stops a client from stepping past a limit by rotating the low 64 bits
of its address. An IPv4-mapped IPv6 address (`::ffff:1.2.3.4`) unwraps to plain IPv4, so the same
client reached through a dual-stack listener counts once rather than twice. Plain IPv4 is
unchanged. On dual-stack deployments, size `MAX_CONNECTIONS_PER_IP`, `MAX_SOCKETS_PER_IP`,
`MAX_TURN_REQUESTS_PER_IP`, `MAX_CODE_REQUESTS_PER_IP`, and `MAX_FAILED_CODE_RESOLVES` for a whole
IPv6 `/64` rather than a single address.

## Room codes

A room code is three random words joined by hyphens, drawn from the 1,247-word list in
`server/words.json` with `crypto.randomInt`, a cryptographically secure source rather than
`Math.random`. The list is the EFF short word list without its hyphenated entry and without words
that read badly in a shared code. The secure source matters because the code is the only secret
guarding the transfer.

On a collision with a code that is still live, the server draws again, up to 10 times, and only
if all 10 collide does it fall back to a four-word code. An expired code counts as free.

A code lasts 10 minutes at most, and the server retires it sooner when its room pairs, empties or
registers a new code, or when the server restarts. What each of those means for the people sharing
a code is in [How a transfer works](/how-it-works/signaling#code-and-link-lifetime). One more event
retires a code: a request link's host making its room on that id, which retires every code
registered for it in any letter case. Resolving a code never retires it, so a receiver that fails
after the lookup and before it takes its seat can retry the same code.

## Global statistics counter

The homepage shows a public, all-time total of bytes transferred by everyone. Because file data
never reaches the server, the counter is fed out of band: after a transfer completes the
**receiver** reports the number of bytes it received. Only the receiver reports, so each transfer
is counted once, and the data-channel protocol is unchanged.

One case reports without completing. A request link drop can stop after the person at Floe
Desktop accepted it. Floe Desktop then reports the bytes of the files it saved under their final
names, once, and only with **Contribute to global stats** on. A drop that completes is reported by the receive
itself, so no drop counts twice, and the CLI reports completed transfers only.

The total is **viewable only in the browser**. The CLI and Floe Desktop contribute to it when they
receive, and never fetch or display it.

The server keeps the running total in two places. An in-memory value answers every read, so
homepage polling never touches Redis. Without Redis configured the counter is memory-only and
resets to zero on restart. With it, the total lives in Upstash Redis under the key
`floe:bytes_total`:

- At startup the server reads the key once and seeds the in-memory value from it.
- Each accepted report adds to the in-memory value at once, and its bytes go to the key in an
  `INCRBY` over Upstash's REST API, without the report waiting for the answer. One `INCRBY` is on
  its way at a time: the bytes of reports that arrive meanwhile are added up and sent in the next.
- Each answer to `INCRBY` is the stored total, and raises the in-memory value to it.

The in-memory value only ever rises. If the startup read fails, the homepage shows a lower total
until the first report's answer restores the stored one. A server image of version 1.11.0 or
earlier ignores those answers, so it shows the lower total until its next restart.

Guardrails are deliberately light: a per-IP [rate limit](/glossary#rate-limit) and a per-report
size cap. The figure is an honest best-effort metric rather than an audited count. The stored value
is a single anonymous integer with no file names, no per-transfer rows, and no link to any user or
IP. Every receiving surface can opt out, and the opt-out happens on the client before any request
is made; the server has no role in it. The switch on each surface is listed under
[Aggregate statistics](/security-privacy#aggregate-statistics).
