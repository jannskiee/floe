Your files travel between two devices encrypted end to end: directly when a direct path exists, and
through a relay that cannot read them when it does not. Floe's signaling server introduces the two
devices and never receives file data. The rest of this page is the detail behind those two
sentences, down to what each app leaves on your own device.

For the other half of an honest answer, the limits of all this, see
[Known limitations](/how-it-works/known-limitations).

## The short version {#the-short-version}

Your files go only to the other person's device,
[encrypted end to end](/glossary#encrypted-end-to-end). Floe's servers, and the services floe.one
runs on, can see that devices connect and from which network addresses, but never a file. The only
thing the server stores for good is one shared byte total, which says nothing about you and which
you can opt out of.

| Who | What they can see |
| --- | --- |
| The other person's device, the [peer](/glossary#peer) | Your files, and your [IP address](/glossary#ip-address) on a direct connection, which [Hide my IP](/glossary#hide-my-ip) prevents |
| Floe's [signaling server](/glossary#signaling-server) | Your IP address while you are connected, the room id, and the byte count a receiver reports. See [What the signaling server can see](#what-the-signaling-server-can-see) |
| The [relay](/glossary#relay), which is Cloudflare on floe.one | Each device's IP address on every transfer, and the timing and size of what it forwards. See [What the relay can see](#what-the-relay-can-see) |
| Sentry and Umami, on the floe.one website only | Errors and anonymous page views, never the room secret. See [Error monitoring and analytics](#error-monitoring-and-analytics) |

## What the signaling server can see

The server at `api.floe.one` exists so two devices can find each other. It never touches the file.

What it does:

- Put two devices in a [room](/glossary#room) and decide which one sends. For a
  [request link](/glossary#request-link), the Floe Desktop that made it is the one that receives.
- Pass the connection-setup messages between them. It checks the size and shape of each one,
  forwards it, and keeps no copy.
- Hand out relay credentials, the temporary user name and password a device needs to use the
  relay, when a relay is configured. Each set is valid for 24 hours and is not tied to you or to an
  account. On floe.one a new set is minted from Cloudflare every few minutes
  and served to every client that asks in the meantime.
- Map a three-word [room code](/glossary#room-code) to a room id when a sender asks for one, for
  10 minutes at most. See
  [How long a code and a link last](/how-it-works/signaling#code-and-link-lifetime).
- Keep a single running total of bytes transferred, for the counter on the homepage.

What it never does:

- Receive, store, or inspect file data. File names and sizes travel between the two devices on
  the encrypted channel, and the only size the server is ever told is the byte total under
  [Aggregate statistics](#aggregate-statistics).
- Keep a record of who joined which room after the room has closed.
- Log what you transfer, your file names, your IP address, a room id, or who you sent to.

Once the [data channel](/glossary#data-channel), the encrypted connection between the two devices,
is open, the server plays no further part in moving the files.

### What it holds, and for how long {#what-it-holds}

Everything in this table lives in the server's memory only, so a restart forgets all of it, and
none of it is written to a log. The byte total under
[Aggregate statistics](#aggregate-statistics) is the one thing the server stores for good.

| What | Held until |
| --- | --- |
| The room id, and which two connections are seated in the room | The last device leaves the room |
| A room code and the room id it stands for | The code is retired, which is about 10 minutes after it was made at the latest |
| Your IP address | You disconnect, and for rate limiting about 2 minutes after your last request |
| The room seal: a keyed hash of the network address of each device that has sent connection-setup messages through the room, never the address itself | The room closes |
| For a request link: a hash of its secret token, never the token, with the times the link was made, joined, left and is due to end | The link ends, or about 10 minutes after the Floe Desktop that made it disconnects |
| For a request link that has ended, or whose Floe Desktop has been gone for more than about 10 minutes: its room id and end time, with a mark that it was used or ended | 24 hours after it was closed, or 24 hours after its end time |
| For the request-link limits: when each network made new links and how many it has open, under a keyed hash of the network address | 24 hours for each new link, and for as long as a link stays open |

A keyed hash is a scrambled stand-in for an address. The server can tell two stand-ins apart but
cannot turn one back into the address, and after a restart they mean nothing. Technically it is an
HMAC, a hash made with a secret key, under a secret the server draws when it starts and never
stores. It covers a whole IPv4 address, or the first half of an IPv6 address (its /64), which
normally names one network rather than one device.

The room seal is what lets the server turn away a device on a third network, as
[A room holds exactly two people](/how-it-works/signaling#a-room-holds-exactly-two-people)
describes. The request-link limits themselves are listed under
[Turn on request links](/self-hosting/request-links#request-link-limits).

## What the relay can see

When a direct path is impossible, traffic goes through a [TURN](/glossary#turn) relay. On floe.one
that is Cloudflare's Realtime TURN network; a [self-hosted](/glossary#self-hosted) instance can run
its own coturn instead.

The relay sees encrypted packets, plus the metadata that being the middle hop entails: both IP
addresses, and the timing and size of what it forwards. The relay's operator may log that for its
own security purposes: on floe.one that is Cloudflare, not your own internet provider.

The relay does not see the contents of those packets. Files are encrypted before they reach it and
decrypted only on the recipient's device.

On floe.one, Cloudflare sees each device's IP address and connection timing on every transfer,
direct ones included. That is because the relay's operator is contacted before the route is
decided. While a connection is being set up, every device asks the [STUN](/glossary#stun) server
for its public address. Unless relay fallback is off, it also reserves a standby path through the
relay, a TURN allocation. File data crosses the relay only when the relay path is the one that
wins.

Routing through a relay also changes who learns your IP address. On a
[direct connection](/glossary#direct-connection) the two devices learn each other's, which is how
any [peer-to-peer](/glossary#peer-to-peer) connection works. If you would rather not reveal yours,
Floe Desktop's [Hide my IP address](/desktop/settings#hide-my-ip-address) forces the relay path so
the other person sees the relay instead, and the [CLI](/glossary#cli)'s `--relay-only` flag does
the same. Either way the transfer is then capped at 2 GB, as
[File size limits](/how-it-works/2gb-limit) explains. The web app has no equivalent, but the page a
sender opens from a [request link](/web-app/request-links) has its own
**Hide my IP (relay only, 2 GB per drop)** checkbox.

With a request link, each side learns the other's IP address as soon as the sender connects,
before anyone accepts or declines, unless that side has Hide my IP on. See
[Who sees your IP address](/desktop/request-links#who-sees-your-ip-address) if you made the link,
and [What each side can see](/web-app/request-links#what-each-side-can-see) if you are sending
through one.

## The room secret stays out of every server log

A [share link](/glossary#share-link) keeps the room id in the
[URL fragment](/glossary#url-fragment), after the `#`, never in the query string, the part after a
`?` that servers do receive. A link from the
web app or Floe Desktop looks like `https://floe.one/?s=a1b2c3d4#room=...` (the web app starts it
with the address you opened the site at), and one from the CLI looks like
`https://floe.one/#room=...`. The `?s=` value is a random per-link marker carrying no information;
it exists only so each link is a distinct page, which stops a device that already has Floe open
from reusing a stale tab.

Browsers never send the fragment to a server. So the room id is not in the web host's access logs,
and not captured by page view analytics or third-party trackers. Nor is it in the `Referer` header,
the address a browser passes on to the next site when you click a link that leaves Floe. The signaling server is the one server that does learn it, because
devices join the room by it. A sender in the CLI or Floe Desktop also sends it when it asks for a
room code. The server holds the room id in memory while the room is open and writes it to no log.

`floe receive`, `floe send --to` and Floe Desktop also refuse a pasted floe.one link while they
are set to use another server, and a link from another Floe server while they use floe.one by
default. They stop before contacting any server, so in those two cases the room id never leaves
the device.

A [request link](/desktop/request-links) looks like `https://floe.one/r/<link id>#<key>`. The key
after the `#` is that link's room id, so it is the request link's secret, and it stays out of logs
the same way. The link id before it is not secret. It sits in the address path, so it reaches the
web host's request logs. It exists so that a report, or a block on one address, can name one link
without the key. The signaling server never receives the link id. On that page, Sentry strips the
link id from the address before a report is sent, Umami does not load at all, and the browser sends
no referrer.

A link is only as private as the way you send it. Mail security services that rewrite links may
see the whole link, the part after the `#` included.

## Aggregate statistics

The homepage carries a public, all-time count of bytes moved across every Floe user. To feed it,
the **receiving** side reports how many bytes it received after a transfer completes. Floe Desktop
also reports a request link drop that stops after it was accepted, with the bytes of the files it
saved. The sender never reports. All three receivers contribute, and the total itself is only ever
displayed in the browser.

What is recorded: one cumulative integer. Nothing else.

What is not recorded: file names, contents, per-transfer rows, who sent or received, or any link
to your identity or IP address. The reported figure is a size, added to a running total. A
transfer of only empty files reports nothing.

<StatsOptOut />

The counter is an honest best-effort metric with lightweight guardrails, a
[rate limit](/glossary#rate-limit) per address and a size cap per report. It is not a tamper-proof
audited figure, and reporting never blocks or slows a transfer. There is no server-side switch that
refuses reports, so opting out is a choice each receiver makes on its own device. On a self-hosted
instance the counter is local to that server, and without a Redis database configured it lives in
memory and resets on restart.

The homepage reads the total every 10 seconds and never shows it going down while the page is
open. It reads 0.00 Bytes until the server first answers, so on a self-hosted instance that figure
can mean the page cannot reach the server. A receive in the same tab that reports adds its bytes
to the figure at once.

## Error monitoring and analytics

<Info>
  Sentry and Umami run on the floe.one website only. The CLI and Floe Desktop contain no analytics,
  no error monitoring, and no telemetry.
</Info>

Beyond the transfer itself, and the requests you ask for yourself (`floe update`, or **Test** in
Floe Desktop's Settings), the CLI and Floe Desktop make two kinds of request on their own. Each has
an off switch: the byte-count report above, and an update check.

The update check runs once a day in Floe Desktop (GitHub builds 0.2.3 and later). The CLI does it
only when you run `floe version`, at most once a day, and never during a transfer. It asks GitHub
whether a newer release exists. The request carries nothing about you beyond what any web request
reveals, and nothing downloads or installs by itself. Turn off **Check for updates** in the
desktop [Settings](/desktop/settings#check-for-updates), or set `FLOE_NO_UPDATE_CHECK=1` for
either surface, and no request is made. Microsoft Store builds never check, because the Store
updates them.

On the floe.one website:

- **Sentry** records application errors and a 10% sample of page performance traces. It is
  configured to attach no cookies and no IP address.
  - Each report carries the page address, the browser's user agent (its name and version),
    language and time zone, and the referring page.
  - An error report, or a performance trace that falls in the 10% sample, may add the connection
    type, whether relay fallback was on, the transfer's progress, the file count, and the total
    size.
  - An error report, or a performance trace in the 10% sample, also carries a short trail of what
    happened just before it. The trail lists clicks, page changes, the addresses of network
    requests, and console lines, with the room link removed from each.
  - A report of a failed receive may also add the device's approximate memory.

  Sentry's servers see the IP address a report arrives from, as any server does. Each report is
  sent with an empty location field, which keeps Sentry from working out a location from that
  address. The room secret is stripped out of every error report, breadcrumb, and performance
  trace before it is sent, and a report the stripping fails on is not sent at all.
- **Session replay is not enabled and will not be added.** A replay records the page address, and
  on a receiver page that address contains the room link, which is the only thing protecting the
  transfer.
- **Umami** records cookieless, anonymous page views and a few events:
  - Page views carry the page path, the referring site, the browser, operating system, device
    type, screen size, language, and a location down to city. The location is worked out from the
    IP address, which Umami says it does not keep.
  - Transfer outcomes: file count, total bytes, whether you were sending or receiving, direct or
    relay, and success or failure with one of 9 fixed reason labels.
  - Which download button was clicked, and the name of an
    [in-app browser](/glossary#in-app-browser) the site was opened in, with whether it was Android
    or iOS.

  It is configured to send neither the URL fragment nor the query string, so the room secret never
  reaches it. It sets no cookies and cannot follow you to other sites. It can recognize a
  returning visitor for a while from a scrambled value that changes on a schedule. If your browser
  sends Do Not Track, a privacy setting many browsers offer, it records nothing at all.

Both are enabled only when their key is supplied. The published container image sets neither, so a
self-hosted instance ships with both off unless you add your own.

### Other services floe.one relies on {#other-services}

Five more companies can see a request, and none of them sees a file.

| Service | What it does for floe.one | What it can see |
| --- | --- | --- |
| Vercel | Hosts the web app. | The IP address and page address of each request, which it may log, as any web host can. |
| Microsoft Azure | Hosts the signaling server. | The IP address of each connection to the server, which the host and the [reverse proxy](/glossary#reverse-proxy) in front of the server may log. The server itself logs none. |
| Google's public STUN servers, `stun.l.google.com` and `stun1.l.google.com` | A fallback when the server's own connection list cannot be fetched, and the default on a server with no relay. | Your IP address, and nothing about the transfer. |
| Mintlify | Serves these docs at floe.one/docs. | Requests for docs pages, and page-view data it may collect with its own scripts. |
| GitHub | Hosts the CLI and Floe Desktop releases. The install script that floe.one serves asks `api.github.com` for the newest release, then downloads it and its `checksums.txt` from `github.com`. The update checks and `floe update` ask GitHub too. | The IP address of each request, and which release was asked for. |

An app falls back to Google's STUN servers when the signaling server is unreachable, or is limiting
requests from your network.

A self-hosted instance uses neither of the first two. Until you configure a relay it uses Google's
STUN servers on every connection, because the server then hands every client those two Google
STUN addresses. With a relay configured, only the fallback in the table does. See
[TURN relay](/self-hosting/turn-relay).

One more service never sees a request from you. The total behind the homepage counter is stored as
a single number in a Redis database at Upstash, written by Floe's server and never by your device.

See the full [Privacy Policy](https://floe.one/privacy) for the site-wide detail. It shows the
month it was last updated, and its **See every change on GitHub** link lists every change made to
it.

## What stays on your device {#what-stays-on-your-device}

Nothing in this section is sent anywhere. It is what a shared or borrowed computer still holds
after a transfer, and how to remove it.

### In the browser {#on-your-device-browser}

Local storage, session storage and Cache Storage are places where a browser keeps a site's data on
your device. Clearing the site's data in your browser's settings empties all three.

| What | Where | Until |
| --- | --- | --- |
| Files you have received and not yet saved | The page's memory. In Chrome and Edge, part of a large file sits in the browser's own temporary files on disk | You close or leave the page. A file you saved is an ordinary download from then on |
| Your **Contribute to global stats** choice | Local storage, key `floe:report-stats`. It is written on your first visit to the homepage, whether or not you receive anything | You clear the site's data |
| The time of the last automatic reload after a new version of the site was deployed | Session storage, key `floe:stale-bundle-reloaded-at` | You close the tab |
| On a request link's page, two numbers while a drop is sending: how many files have arrived and how many there are | Session storage, key `floe:r-lost` | The drop ends. If the browser discarded the tab first: that tab loads again, or you close it |
| Five of the site's own pages (the home page, Download, How it works, Privacy and Terms) and its build files, so they open without a network. Nothing transfers without one | Cache Storage, written by the site's service worker | You clear the site's data |

That cache never holds a share link, a request link's page, an answer from the server, or these
docs. The web app sets no cookies, uses no IndexedDB, writes to your clipboard only when you press
a copy button and never reads it, and never asks for notification permission. How much a browser
can hold while it receives is under
[A browser receiver is limited by what the browser can hold](/how-it-works/known-limitations#a-browser-receiver-is-limited-by-what-the-browser-can-hold).

### In Floe Desktop {#on-your-device-desktop}

| What | Where | Until |
| --- | --- | --- |
| Settings | `%APPDATA%\floe\desktop.json`. A file Floe could not read is kept beside it as `desktop.json.bad`. See [Where settings are stored](/desktop/settings#where-settings-are-stored) | You delete the file. Uninstalling leaves it |
| History: the last 50 transfers, with file names, folders, sizes and times, and for a request-link drop your label | The app's [WebView2](/glossary#webview2) profile, `%APPDATA%\floe\webview` | You remove a row or clear the list, as [History](/desktop/receiving#history) shows, or delete the folder. Reset and uninstalling leave it |
| A request-link drop that is still arriving: its label, its counts and sizes, its folder, up to 200 saved file names, and when it was last written, so a drop Floe was closed during still gets its History row | `%APPDATA%\floe\quit-drop.json` | The drop ends, or the next time Floe starts, which reads it once and deletes it |
| Your save folders, the tab you last used, your right-click menu choice, and, while a request link is open, the time it ends | The same profile | You delete the folder |
| The update check's last answer (GitHub builds) | `%APPDATA%\floe\desktop-update-check.json` | The next check overwrites it, or you delete it |
| The **Send with Floe** right-click entry (the installer build from GitHub, and the portable build once you turn it on) | A per-user registry key, `HKCU\Software\Classes\*\shell\Floe` | You turn off [Show in right-click menu](/desktop/settings#show-in-right-click-menu), or uninstall the installer build |
| The name Windows shows on Floe's notifications (GitHub builds) | A per-user registry key under `HKCU\Software\Classes\AppUserModelId`, and a small icon file in your temp folder | You delete them. Uninstalling leaves them |
| A pasted screenshot waiting to be sent | A folder whose name starts `floe-paste-` in your temp folder | The next time Floe starts |
| A text note being sent | A folder whose name starts `floe-text-` in your temp folder | That transfer ends, or Floe quits. One left by a crash is removed the next time Floe starts |
| A file that is still arriving | A `.part` file beside the place the finished file will take | It finishes and takes its real name, or the transfer fails or is canceled and the `.part` is deleted. A power loss, a forced quit or a failed final rename can leave one: see [If a transfer stops partway](/desktop/receiving#if-a-transfer-stops-partway) |

A registry key is an entry in Windows' own settings database, and `HKCU` is the part of it that
belongs to your user account. A request link itself, its key and its secret token are held in
memory only and are never written to disk. Received files stay where they were saved until you delete them, and on a drive that
supports it Floe marks each one as a download: see
[Received files are marked as downloads](/desktop/receiving#received-files-are-marked-as-downloads).
[Uninstall](/desktop/installation#uninstall) lists what removing the app leaves behind.

### On the command line {#on-your-device-cli}

The CLI keeps no history, no log, and no settings file. It leaves two things:

- **The update check's last answer.** `floe version` saves it in `floe/update-check.json` inside
  your user config folder and reuses it for 24 hours. See
  [The update check](/cli/version#the-update-check).
- **The files you received**, in the folder you named with `-o` (the folder you ran the command
  in, by default). Each file is written as a `.part` beside its final name and renamed when it is
  complete, and a receive that fails or is interrupted deletes the unfinished `.part`. One can
  remain after a killed process, a power loss, or a finished file that could not be renamed: see
  [floe receive](/cli/receive#part-files). On Windows each finished file carries the same download
  mark as in Floe Desktop.

## Browser hardening

In short, no other website can show floe.one inside its own page. The rest of this section is the
technical detail, and you can skip it.

floe.one sends a Content-Security-Policy with `frame-ancestors 'none'`, repeated as
`X-Frame-Options: DENY` for older browsers, so no other site can put Floe in an iframe.

That matters more here than on a typical site. A receiver page joins its room automatically on
load and then answers the sender's offer with its own network addresses. An invisible embedded
copy pointed at an attacker's room could otherwise disclose a visitor's local and public IP
addresses without a single click.

The same headers also:

- block plugin content and `<base>` rewriting
- restrict form submissions to the site itself
- send `X-Content-Type-Options: nosniff`
- set `Referrer-Policy: strict-origin-when-cross-origin`
- deny camera, microphone, geolocation, payment, and USB access outright
- opt the site out of ad interest cohorts

A request link's page sets `Referrer-Policy: no-referrer` instead, because its link id is in the
address path. The signaling server sends the standard hardening headers too.

## On a self-hosted instance

A self-hosted server runs the same code, so everything above about what the signaling server sees
and holds applies to yours, with you as the operator. The parts that name Cloudflare, Sentry, or
Umami describe floe.one's own deployment. Most of the per-address limits are yours to set: see
[Configuration](/self-hosting/configuration).

The signaling server never receives file data and a relay only ever forwards encrypted packets, so
running your own instance gives you the same encryption and puts the infrastructure under your
control.

It also removes the one dependency that encryption alone cannot cover, described in
[Known limitations](/how-it-works/known-limitations#the-signaling-server-is-trusted-to-introduce-you-honestly).

See [Self-hosting overview](/self-hosting/overview) to run one.

## Reporting abuse {#reporting-abuse}

Floe cannot see, store or remove the files people send each other. Its server keeps no record of
who joined which room once the room has closed. Relay credentials are shared by everyone who asks
within the same few minutes, so Floe cannot identify a sender afterward or cut off one person's
relay access.

If someone sent you something harmful:

- Do not open more links or codes from that sender. A transfer starts only when you open one, and
  `floe receive` asks before it accepts files.
- Report it on Floe's public [issue tracker](https://github.com/jannskiee/floe/issues). When the
  report includes personal details about anyone, or the content itself, send it privately instead,
  through the channels under [Reporting a vulnerability](#reporting-a-vulnerability).
- For a request link, use **Report this link** on its page: see
  [Report a link](/web-app/request-links#report-a-link). Never post a whole request link in
  public, because the part after the `#` lets anyone use it.

## Reporting a vulnerability

Report security issues privately through
[GitHub Security Advisories](https://github.com/jannskiee/floe/security/advisories/new) or the
contact in [SECURITY.md](https://github.com/jannskiee/floe/blob/main/SECURITY.md). Please do not
open a public issue, which would expose the problem before there is a fix.
